### `setup_cmd.py`

Implements `sysforge setup` — one-shot pre-flight that stops `pacman -Syu` from silently clobbering sysforge-built packages with upstream repo binaries. It inspects `/etc/pacman.conf` for `IgnoreGroup = sf-build` and, if missing, offers to add it (interactive prompt). Packages built by sysforge carry the `sf-build` group, so the IgnoreGroup line gates the whole rebuild surface behind a single policy knob rather than requiring a per-package `IgnorePkg`.

Public API: `cmd_setup(args)`. Flag: `--pacman-conf PATH` (default `/etc/pacman.conf`) for VM or chroot runs where the file lives elsewhere. No effect if the line is already present. Intended to be run once after first installing sysforge; safe to re-run.

`setup` also installs/refreshes sysforge's **libalpm hooks** after the IgnoreGroup step. The three shipped hooks (`sysforge-kernel.hook`, `sysforge-toolchain.hook`, `sysforge-buildstate.hook`) plus `pacman-hook-helper.sh` are the input side of `update`'s reminder/auto-demote logic; the PKGBUILD installs them at package time, but a **source-checkout dev workflow** (or an edited hook) leaves them missing or stale, silently disabling that logic. Hook provisioning has one home — `primitives/pacman_hooks.py` — which resolves the canonical source (repo checkout preferred, else the wheel's bundled `sysforge/_data/` copy shipped via a `force-include` in `pyproject.toml`), byte-compares it against the installed copy (`diff_status` → `ok`/`missing`/`stale`), and writes the missing/stale files through `fs_provision._run_priv` (the existing sudo-or-fail path; no second sudo path). A privileged failure prints a "re-run with `sudo sysforge setup`" hint rather than crashing. The same `diff_status` facts are surfaced read-only by `doctor --pacman` (`doctor._collect_hook_findings`, a warning per drifted hook). `tools/check_shipped.py::check_hooks` asserts `pacman_hooks.HOOK_NAMES` matches the shipped `.hook` files and that the `force-include` ships the hooks dir + helper.

**Presets step (`3.5.0-F9`).** Between the hooks and the preferences, `_setup_preset()` offers one preset from `primitives/config_presets.py` (`PRESETS`, a pure table of `PresetRow(target, section, key, value, default)`; `PRESET_NAMES` feeds the CLI `choices`, the menu and the completions test): `defaults` (writes nothing), `performance` (`[defaults] profile = "optimized"`, `toolchain = "llvm"`), `low-friction` (`confirm_plan = false`, `review = false`, `sandbox_builds = false`, `auto_fetch_pgp_keys = true`, toolchain `reuse_unchanged = true`) or `secure` (`profile = "hardened"`, `confirm_plan`/`review = true`, `sandbox_builds = true`, `auto_fetch_pgp_keys = false`, kernel `hardening = true`). Each row's live value is read from its resolved file (profiles via `_active_profiles_path`, or, under `sudo`, the invoking user's own `~/.config/sysforge/profiles.toml` when it exists (`_invoking_user_profiles`: root's home would hide the file that shadows the system one for that user's builds, and the hardened-profile guard checks that same view through `_resolved_profiles`); packages via `resolve_packages_path`, the rest from `paths`), falling back to the row's shipped `default` when the key is unset, and only differing rows are planned, so re-applying a preset writes nothing; `tests/test_config_presets.py` pins every row's key and default against `etc/sysforge`. Two guards turn a row into a printed note: a profile the resolved profile config cannot see (a user `profiles.toml` without `extends_system` replaces the system file; for `hardened` the note is the block to paste), and `sandbox_builds = true` without devtools and the chroot (`_sandbox_ready`, shared with the preferences step). The plan prints as `key: old → new` (glyph via `render.arrow`) with the preset's notes (low-friction's review-off warning and the sandbox note, since the sandbox is off once it applies; for performance, a warning when `toolchain.toml` has the stage enabled with a non-llvm `compiler`, because the stage's `propagate_default_toolchain` would reset `[defaults] toolchain` on its next run), then a terminal run asks `Apply? [y/N]`; `--preset NAME` is the consent and skips the menu and the confirm at a terminal or not, while no terminal and no flag skips the step. Writes go through `_write_rows`, shared with the preferences step: `[defaults] toolchain` via `config.set_default_toolchain` (its one home), the rest via `config.set_toml_key`, whose `section=None` form writes the top-level `hardening`/`reuse_unchanged` keys above the first table header; a failed write prints the manual line and the remaining rows still apply. Presets never touch the stages' `enabled` keys or `checksum_mismatch`. The preferences step then reads the written values as its current answers.

**Preferences step (`3.1.0-F4`).** After the hooks, `_setup_preferences()` asks four questions at a terminal (stdin *and* stdout TTYs, `_has_terminal()`; otherwise it prints `preferences: skipped (no terminal)` and returns): whether `update` confirms its plan (`[build] confirm_plan`, yes/no), how changed AUR/git sources are treated (`[build] review`: `[r]eview` / `[a]ccept and record` / `[o]ff`, the current mode read through `pkgbuild_review.resolve_review_policy`), whether to use the AUR (`sysforge.toml [aur] enabled`), and whether to build in the clean chroot (`[security] sandbox_builds`). The sandbox question is asked only when `makechrootpkg` is on `PATH` and `<sandbox_chroot_dir>/root` exists; otherwise setup prints the two commands that set it up. Choosing `accept` prints the risk text, plus a note that the sandbox does not inspect what gets installed when the sandbox is off. Enter keeps the current answer, and only changed answers are written, each through `config.set_toml_key` (the one runtime TOML writer, which escalates for a root-owned `/etc/sysforge`); a failed write prints the `[section]` / `key = value` lines to add by hand. Not reached when `pacman.conf` is missing (the verb returns before the IgnoreGroup step).
