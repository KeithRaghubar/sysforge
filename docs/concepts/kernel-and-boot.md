# Kernel Builds and Boot Basics

What goes into building your own Linux kernel and getting it to boot: the kernel
configuration, modules, the initramfs, boot loader entries, and why you always keep a second
kernel to fall back to.

The [glossary](glossary.md) defines the terms these pages share.

---

## The kernel configuration

The kernel source supports far more hardware and features than any one machine needs. Which
of them a build includes is decided by its configuration, a `.config` file of several thousand
lines such as:

```
CONFIG_EXT4_FS=y
CONFIG_BTRFS_FS=m
# CONFIG_REISERFS_FS is not set
CONFIG_HZ_1000=y
```

The options and their dependencies are declared in `Kconfig` files throughout the source, and
the kernel's configuration tools work out what is allowed: an option that depends on another
cannot be on while that one is off.

You rarely write a config from scratch. The usual starting point is an existing one, such as
your distribution's (Arch ships it in the kernel package's source, and a running kernel built
with `CONFIG_IKCONFIG_PROC` exposes its own at `/proc/config.gz`). Then:

| Command | What it does |
|---|---|
| `make olddefconfig` | Takes the existing `.config`, keeps every answer it has, and gives every option it does not mention (new in this kernel version) its default, without asking. |
| `make oldconfig` | The same, but asks about each new option. |
| `make menuconfig` / `nconfig` | Interactive menus for changing options by hand. |
| `make localmodconfig` | Turns off every module that is not loaded right now. |
| `scripts/config` | Sets single options from a script, for example `scripts/config --enable FOO`. |

A **config fragment** is a short file listing only the options you want to change. Merging it
into a base config (`scripts/kconfig/merge_config.sh`), then running `olddefconfig`, keeps
your changes small and makes them survive kernel updates, since the base config is refreshed
underneath them.

`localmodconfig` makes builds much faster and the kernel smaller, but it only knows about
hardware in use while it runs. A USB device that was unplugged, a filesystem that was not
mounted or a network protocol that was not used at that moment is turned off, and the new
kernel cannot use it until you rebuild.

## Built-in or module

Most drivers and features can be built two ways:

- **Built in (`y`)**: part of the kernel image itself, always present from the first moment
  of boot.
- **Module (`m`)**: a separate `.ko` file under `/usr/lib/modules/<kernel version>/`, loaded
  only when needed (usually automatically, when the hardware is found).

Modules keep the image small and let a distribution support every machine with one kernel. A
module can only be loaded once the root filesystem, or an initramfs (below), is available, so
whatever is needed to reach the root filesystem (the storage controller driver, the filesystem,
disk encryption, LVM or RAID) must be either built in or included in the initramfs.

Modules are tied to the exact kernel build they were compiled for. Drivers maintained outside
the kernel tree, such as NVIDIA's, are rebuilt for each new kernel by **DKMS**, which needs the
matching kernel headers package to be installed.

## The initramfs

The kernel cannot mount a root filesystem it does not have the driver for, and those drivers
are usually modules stored on that same filesystem. The initramfs solves this: a small
compressed archive the boot loader loads into memory alongside the kernel. It contains a
minimal userspace with the modules and tools needed to find and mount the real root (unlock
an encrypted disk, assemble RAID, activate LVM). Once the root is mounted, it hands over to
the real system.

On Arch the initramfs is generated by `mkinitcpio` (or optionally `dracut` or `booster`) for
each installed kernel, from a pacman hook whenever a kernel is installed. mkinitcpio usually
builds two images per kernel:

- **The default image** includes only the modules this machine needs (its `autodetect` hook).
- **The fallback image** includes all modules, for when the default one does not boot, for
  example after a hardware change.

## Boot loaders and entries

At power-on, UEFI firmware runs a boot loader from the EFI system partition, and the boot
loader loads a kernel image, its initramfs and a kernel command line. Which kernels it offers
depends on the boot loader:

- **systemd-boot** reads one small text file per entry from `/boot/loader/entries/`, in the
  format of the [Boot Loader Specification](https://uapi-group.org/specifications/specs/boot_loader_specification/):

  ```
  title   Arch Linux
  linux   /vmlinuz-linux
  initrd  /initramfs-linux.img
  options root=UUID=… rw
  ```

  On Arch nothing writes these entries by default (unless you set up `kernel-install` to), so
  a new kernel needs a new file.
- **GRUB** has one generated menu, `grub.cfg`. `grub-mkconfig` scans `/boot` for kernels and
  writes an entry for each, so a new kernel appears after the next `grub-mkconfig` run.

### Menu order in systemd-boot

The specification orders entries in two groups:

1. Entries **with** a `sort-key` line come first, ordered by `sort-key`, then `machine-id`,
   then `version` (newest first).
2. Entries **without** one follow, ordered by file name compared as versions, highest first,
   so `99-a.conf` lists above `10-a.conf`.

Order is only the menu's layout. Which entry boots when nobody chooses is separate: the
`default` line in `/boot/loader/loader.conf`, or the one set with `bootctl set-default`. To boot
an entry once without changing the default, use `bootctl set-oneshot <entry>` before
rebooting.

## Why a fallback kernel matters

A kernel that fails to boot cannot be fixed from inside itself. If it is the only kernel on
the machine, recovery means booting from a USB stick and repairing the system with
`arch-chroot`. A second, known-good kernel with its own boot entry makes the same failure a
reboot and a menu choice.

So a custom kernel is safest when it:

- **Installs beside the distribution kernel** under its own package name (`linux-custom`
  rather than replacing `linux`), with its own image, initramfs and entry.
- **Leaves the known-good kernel installed** and updated. The stock kernel, or `linux-lts`,
  makes a good fallback because its configuration is tested by many people.
- **Is checked before it is made the default**, by booting it once on purpose (a one-time boot)
  before relying on it.

Keep an eye on the size of `/boot` when several kernels are installed: each one needs its
image and initramfs (and often a fallback initramfs) there, and a full `/boot` makes the next
kernel install fail.

## In sysforge

`sysforge run kernel` builds a kernel from a distribution kernel's PKGBUILD under its own
name, merges your config changes as a fragment, and checks for a fallback kernel and `/boot`
space before building and for boot-critical options before installing; the
[kernel guide](../guides/kernel.md) covers it. On systemd-boot it also writes an entry for each
kernel it builds, which the [boot entries guide](../guides/boot-entries.md) covers.
