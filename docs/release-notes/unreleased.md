## Added

- **`3.1.0-F6` — `update --versions`: the available-version report, without entering a stage.** Answering "is there a newer toolchain or kernel?" previously meant either reading a full `update --dry-run` walk or entering `run toolchain` / `run kernel` itself. `sysforge update --versions` renders a `PACKAGE / INSTALLED / AVAILABLE` table and exits before the build loop, reusing the version check the walk already performed — it costs nothing beyond the check. Only actionable rows are listed (`NEEDS_REBUILD`, `NEEDS_PACMAN_UPGRADE`, `DOWNGRADE`); up-to-date packages collapse into a footer count, a failed check never occupies a row, and unresolved VCS packages become a single `--devel` hint rather than dozens of unknown-version rows. Stage-owned toolchain/kernel packages — which a normal run skips — are always included, annotated with the stage that owns them, sourced from the advisory path that carries that annotation. Mutually exclusive with `--explain-drift` (both are list-and-exit reports) and exempt from the stale-sentinel gate, on the same read-only grounds as `--dry-run`.

## Fixed

- **`3.1.0-B1` — Record the version the build actually produced, not the oldest artifact in PKGDEST.** Build-state recording reverse-engineers `pkgver`/`pkgrel`/`epoch` from built `.pkg.tar.*` filenames, but took the *first* match a directory glob yielded. When `PKGDEST` is a shared, long-lived package archive holding every historical build (the common `/home/packages` layout), that first match is an arbitrary — in practice the oldest — version, so `build_state.toml` recorded a years-stale `pkgver` as "last built". The next run's `vercmp` then saw the on-disk PKGBUILD as newer, reported "upstream PKGBUILD has moved", and rebuilt the package again, indefinitely. Artifact selection now goes through `select_built_version()`, which considers only filenames parsing as the target pkgname and picks the most recently modified — the one the build that just finished produced. A local state file showed 69 affected packages.

---

- **`3.1.0-B2` — Stop advertising a drift-rebuild flag in the same run that already acted on it.** The toolchain- and flag-drift advisories printed "Pass `--rebuild-on-toolchain-drift`/`--rebuild-on-flag-drift` to rebuild" unconditionally whenever drift was detected, including when that rebuild was already enabled via the flag, the per-axis `[update]` key, or the `rebuild_on_drift` umbrella. A run would emit the "pass this flag" hint immediately above "promoted 26 UP_TO_DATE package(s) to NEEDS_REBUILD", making legitimate same-version rebuilds read as spurious reinstalls. The drift axes are now resolved before the advisories, which report `rebuilding (--rebuild-on-flag-drift)` when the rebuild is already in effect and keep the opt-in hint only when it is not.

---

- **`3.1.0-B3` — Stop pinning repo checkouts to a superseded release when the local sync DB is stale.** `SourceSyncScheduler._pin_repo_checkout` resolved the release tag to check out via `pacman.get_pacman_sync_version`, which reads `/var/lib/pacman/sync/*.db` through pyalpm or `pacman -Si` — neither touches the network. On a rolling repo that means the "available" version is whatever the last `pacman -Sy` left on disk, so a sync DB even a few hours old pins an already-superseded release; the kernel stage reported 7.1.8 as the newest available while the repos carried 7.1.9. The pin now resolves through a new `pacman.get_repo_candidate_version`, which cross-checks the sync DB against `checkupdates_map()` — `checkupdates` refreshes a *side copy* of the sync DBs, so it needs no sudo and cannot leave a partial-upgrade state — and takes whichever version is newer by `vercmp`. It is a strict enrichment: an absent `checkupdates` entry, an unavailable tool, or an older value all fall back to the previous sync-DB answer, and the probe is memoized for the process so one run covers every pinned package. Applies to all `source = "repo"` pins, not just the kernel.

---

- **`3.1.0-B6` — Stop forcing maximum verbosity on every `--dry-run`.** `log.set_dry_run_mode()` set `_VERBOSITY = 3` unconditionally, and `cli.main` called it *after* resolving the user's verbosity — so `--dry-run` overrode `-v`, the `[log] verbosity` config key, and even `--quiet`. A dry-run on a 190-package install emitted 2249 lines, 1701 of them `[DEBUG]` profile dumps, burying a six-line answer. The forcing predates the `ui()` level, when max verbosity was the only way a dry-run printed anything; it is now removed, and `set_dry_run_mode()` only redirects output to stdout (which was always correct). Four dry-run *verdicts* whose real-run counterparts raise — the kernel stage's fallback-kernel and `/boot`-space aborts, and the toolchain stage's Gate 1 findings — were emitted at `warn()` and would have gone silent at the shipped default; they are re-levelled to `ui()`, matching the rubric's existing "dry-run previews are `ui()`" rule. The regression guard drives the real `cli._main()`: the existing `quiet_at_default` fixture reimplements the dispatch order it is meant to guard, applying verbosity *around* `set_dry_run_mode()` where production applies it *before*, which is why this was invisible to it.

---

- **`3.1.0-B8` — Keep the distro's compiler hardening flags across a profile `CFLAGS` override.** `emit_makepkg_conf` merges `/etc/makepkg.conf` with the resolved profile *per key*, not per token, and the shipped `standard` and `optimized` profiles set `CFLAGS` in full — so every package built through them compiled without `-Wp,-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, `-Werror=format-security` or `-fexceptions`, losing run-time buffer-overflow detection, the stack-smashing protector and format-string rejection that the system conf applies by default. That this was an oversight rather than a policy choice is visible in the same profiles' `LDFLAGS`, which carefully keep `-z,relro,-z,now` — the *linker* half of the same hardening set. A new `[preserved_system_tokens]` table in `profiles.toml` declares, per conf key, which tokens of the system value survive an override; they are re-added by `profile.merge_preserved_tokens` with profile-wins precedence — a profile that already names the token, names a conflicting one in the same `[append_conflict_groups]` group (`-fno-stack-protector`), or names one in the same flag family (`-Wp,-D_FORTIFY_SOURCE=2`) keeps its own value, so opting out stays possible and explicit. Only tokens the system conf actually sets are restored, so nothing is invented on a distro that omits them; `CXXFLAGS = "$CFLAGS"` inherits by shell expansion rather than injection; kernel builds are unaffected (their flag keys already pass through verbatim). A profile can opt out of the pass entirely with `preserve_system_tokens = false`.

---

- **`3.1.0-B9` — Keep shipped section order when `sync-config` injects a table, so a relocated section can't read as a deleted one.** `sync_config.merge_container` appended every newly-injected table to the *end* of the live file rather than to the position it holds in the shipped default. TOML ignores section order, so the resolved config stayed correct and the defect was invisible at runtime — but the live file's layout diverged from shipped a little further with every sync, and the `.sfnew` adoption step is a line-based `difflib` diff with no move detection. A section sitting at a different offset in the two files therefore renders as a deletion in one hunk and an addition hundreds of lines away in another; read top-down that says "this section is missing from the shipped file", and hand-merging against that reading deletes a live section for real. On a local config this cost `profiles.toml` its entire `[consumes_inference]` table. A new table is now spliced after its nearest shipped-order predecessor that the live file actually has — falling back through the shipped order, and to EOF only when there is no such predecessor — so an already-reordered live file still anchors against a real neighbour, and a run of consecutive new tables stays in shipped order by anchoring on each other. Insertion lands immediately after the anchor's own entry, before any standalone comment run tomlkit holds for the following table, so those comments stay attached to what they document; the write remains idempotent. Defence in depth at the reading end: `config_cmd._diff_text` now prepends a banner naming any section header the diff shows as both removed and added, since a header on both a `-` and a `+` line is present in both files. Pre-existing order drift in a live file is not rewritten — the tool never does a wholesale rewrite of a config it did not lay out.

## Security

- **`3.1.0-F7` — Opt-in build sandbox: run PKGBUILD code in a clean container instead of as you.** A PKGBUILD's `prepare()`/`build()`/`package()` are arbitrary code, and every build ran unsandboxed on the host: `~/.ssh`, GPG material and browser profiles were readable at build time, which is the actual execution vector of the AUR supply-chain campaigns — the payload runs during the build and never has to land in a package at all. `[security]` previously offered only `freeze_sources`, which gates code *ingress*; there was no lever for blast *radius*. New `[security] sandbox_builds` (default `false`) replaces the makepkg invocation with a `makechrootpkg` one, so the build executes inside a clean `systemd-nspawn` container as an unprivileged `builduser` with only the PKGBUILD directory bind-mounted; `sandbox_chroot_dir`, `sandbox_clean` and `sandbox_update` tune the chroot, and a profile can override the switch either way with `sandbox_builds` in `profiles.toml`. The argv *shape* branches rather than composing another throttle prefix, because `makechrootpkg` works on the current directory, cannot honour `-p <name>`, and escalates itself — so a `sudo` of ours would strip its preserved `PKGDEST`/`SRCDEST`/`LOGDEST` and relocate every artifact. Four collaborators move with it: the dest variables are exported from the emitted conf so artifacts land exactly where the host path leaves them; a container-side conf is derived with the dest keys repointed and the env-delivered `CC`/`CXX` re-added as `export` lines (the invocation env does not cross the boundary); `[build] mem_limit`'s `RLIMIT_AS` clamp is dropped with a warning rather than silently capping the wrapper instead of the build; and dependencies built earlier in the run — installed on the host, invisible to the container — are fed back in as `makechrootpkg -I` through a session artifact registry. Preflight refuses rather than downgrades: a missing `devtools`, a missing `<chroot>/root`, or a non-`PKGBUILD` filename each stop the build with the command that fixes it, because a security opt-in that silently falls back to the host hands the user exactly the exposure they opted out of. `run toolchain` and `run kernel` are exempt — both build against, and install into, the host they are upgrading. Rejected alternative: adding `ProtectHome=`/`PrivateTmp=` to the existing `systemd-run --scope` wrapper, which cannot work — `--scope` never execs the command, so systemd rejects exec properties outright. Known scope limit, documented in README and DESIGN and tracked in ROADMAP: the container resolves build deps from the stock repos rather than the host's installed set, so a dependency built in an *earlier* run is not visible to it, and a source-built package ahead of the repos is replaced by the repo version — which is why the feature is scoped at untrusted AUR leaf packages whose deps come from repos. The optimization of the host's own packages is not affected: it lives in their installed binaries, which the built package still runs against.
