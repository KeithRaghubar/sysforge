## Added

- **`2.5.1-F3` — `state failed --clear-all` now emits a `SYSFORGE_TARGET`.** Follow-up to `2.4.0-F1`, which gave every sentinel-gated verb a `journal_target` override. `StateFailedVerb.journal_target` keyed only on `args.clear`, so a `--clear-all` invocation — equally sentinel-gated, since it rewrites `build_state.toml` — fell to `None` and journalled the verb name alone. It was the one spot where 2.4.0-F1's "every mutating verb supplies a meaningful target" goal was not met, which meant `journalctl SYSFORGE_VERB=state-failed` could not distinguish "wiped every recorded failure" from "cleared one package". The clear-all path now emits the subjectless `mode:failed-clear-all` target; `--clear` still wins when both are set, since a named subject is more useful. Observability only — no correctness impact.

---

- **`2.6.1-F28` — `artifact review --all` bulk-adopts every offerable candidate.** Adoption was one-file-at-a-time: `artifacts.adopt` takes a single `src`, reached only through a per-candidate prompt loop, so pointing sysforge at a directory that is already a curated set — a `~/.local/bin` that has accumulated dozens of hand-written scripts — cost one keystroke per file. `--all` iterates the *same* `iter_offerable(registry, ignore)` result the interactive loop walks, which is the whole point: the exclusion rules (package-owned, sysforge-owned, already-managed, declined-and-unchanged) keep a single home and cannot drift between the interactive and bulk paths. It skips candidates whose ownership pacman could not determine unless `--include-unknown` is also given — an unknown owner means the file may in fact be package-owned, and a blind bulk adopt is exactly where that mislabel does damage — respects the ignore list as the interactive loop does, since a recorded decline is a decision, and runs off a TTY, replacing the list-and-hint branch when the flag is given. A per-candidate failure logs and continues, and the run closes with an adopted/skipped/failed count. Low risk by construction: adoption is copy-only, touches no live file, and is undone by `artifact remove --purge`.

- **`3.0.0-F5` — Itemize the flag-triggered `pacman -Syu` in the update summary.** Phase 6.5 has two routes into the same transaction, and only the classified one could report what it did: a `--sysupgrade` / `[build] system_upgrade` run hands the whole transaction to pacman, so the summary knew only that it had happened and printed `system upgrade (pacman resolved the transaction)`. That was honest but strictly less useful than a hand-run `-Syu`, and it was the common case — the managed set rarely holds `build_mode = "pacman"` entries, so the classified list is usually empty precisely when the flag route fires. The block now itemizes `pkg: old → new` for the requested-upgrade route too, from a reporting-only capture that snapshots the local package DB either side of the transaction and diffs the pair (`pacman.diff_installed`). Reading the DB *back* is the point: it reports what pacman actually did rather than what a second resolver predicted, and it needs no `checkupdates` probe — which is what decoupling the flag route removed in the first place. Fresh installs render `(new) <ver>` and removals `<ver> (removed)`. Output is scaled by verbosity, because a stock `-Syu` can be hundreds of packages unlike the bounded managed list: the default view caps the block and closes with `... and N more (-v for the full list)`, `-v` and above print it in full. The capture is on by default, applies only to the requested-upgrade route, and is turned off with `--no-sysupgrade-report`; it is best-effort throughout, so a failed snapshot drops the report and never the run, falling back to the existing single line.

- **`3.1.0-F5` — the first `run toolchain` / `run kernel` on an install now points at the config that drives it.** These are the two stages whose behaviour is decided almost entirely by their TOML rather than by the flags the user typed — `toolchain.toml` picks the compiler and the PGO passes, `kernel.toml` picks the kconfig fragments and initramfs handling — so a user who ran `setup` and then typed `sysforge run kernel` got a kernel built from defaults they had never opened. The existing first-install advisory could not cover this: it keys on the marker the `post_install` scriptlet drops and retires itself the moment `reconfigure` and `hardware` are both done, i.e. it clears *before* anyone reaches toolchain or kernel. `init_notice.maybe_emit_stage_config_notice` now names the config file and the two or three settings most likely to surprise, on both pipeline entry points. "First run" means never *completed*, not never *attempted*, so a failed first attempt re-advises — the config is exactly as unread as it was before, and a failed stage is the one most likely to be retried blind. No new state is needed: `PipelineState.stage_status` already returns `"pending"` for a stage it has never seen. Strictly advisory — it prints, never prompts, never blocks, and never raises.

- **`3.1.0-F9` — a sandboxed build now sees the dependencies you built in earlier runs.** `arch-nspawn` gives the container its own `/etc/pacman.conf`, so `makechrootpkg --syncdeps` resolves build deps from the stock repos and never from the host's installed set. The session registry already fed back packages built *in the same run*, which is why an `update` across a stack resolved — but a one-off `sysforge build cosmic-comp-git` whose `cosmic-protocols-git` was built last week got `error: target not found`, because that dependency exists only as an installed host package. The whole self-built stack was out of the sandbox's reach, which is why the feature was documented as scoped at AUR leaf packages. `build_state.toml` turned out to already carry the right shape to seed from: it is keyed by **pkgname** rather than pkgbase, so split packages arrive pre-expanded, which is exactly what `-I` needs since it takes package *files*. `resolve_dep_artifacts` scopes the injection to the target's dependency closure ∩ source-built — not every source-built package, which on a stack machine is ~150 files copied into the working copy and installed in one `pacman -U` per build — walking the closure over the host's local DB in a single pass, since `build_state` records versions but no dependency edges. Version selection is the part that matters most: the artifact matching what the host *currently runs*, never the newest file in `PKGDEST`, because that directory is a long-lived archive of every historical build (`3.1.0-B1`) and injecting its newest would hand the container a version the host does not have, recreating the very skew the injection removes. That matcher was lifted out of `build_core._find_existing_artifacts` into `makepkg_artifacts.find_artifacts` with a new exact-version mode — `primitives/` cannot import from `build_core`, and a second copy would have drifted — with `build_core` keeping the old name as a delegate. A source-built dep whose artifact was pruned from the archive warns, naming the package and the version being substituted, and continues: the container falls back to the repo version, which is a build-fidelity mismatch rather than a breach of the isolation boundary, and unlike the sandbox's refuse-rather-than-downgrade preflight there is no matching risk to justify a hard stop over a pruned file. `install_args` unions the two sources with the session registry winning, since this run's own builds are newer than anything the store points at. Does **not** fix version skew against packages outside the injection set — a source-built package ahead of `extra` is still replaced in the container by the repo version. That class needs a local pacman repo named in the chroot's own `pacman.conf` and remains open on the roadmap.

- **`3.2.0-B9` — a `SYSFORGE_PTY_RAW_DUMP` capture for diagnosing terminal-state bugs.** The bottom progress bar still disappears for the length of some builds after `3.2.0-B3`, and the existing record cannot answer why: `run_with_pty` relays the child's bytes to a `line_callback` whose consumers run them through `strip_ansi` before anything is written, so the log holds only the visible text. The sequences under suspicion — a DECSTBM reset, `RIS`, an alternate-screen switch, any of which would end the bar's scroll region for the rest of the run — are precisely the ones that filter removes, which means scanning the log for them returns zero whether they were emitted or not. Pointing `SYSFORGE_PTY_RAW_DUMP` at a path appends the child's stream verbatim, before any filtering, and leads the file with the winsize actually handed to the pty (`rows`, `cols`, `reserve`) — the second half of the question, since B3's fix turns on the reservation surviving `makechrootpkg -> sudo -> arch-nspawn -> systemd-nspawn` and a lost reservation and a reset region produce the same symptom. Off unless the variable is set, and best-effort at every step: an unwritable path, a failed write and a failed close are each swallowed, so a diagnostic can never be the reason a build stops. Diagnostic only — it observes the stream and changes nothing about it.

- **`3.2.0-B11` — a `SYSFORGE_PROGRESS_TRACE` record of the bar's scroll-region transitions.** `3.2.0-B9`'s raw pty dump answered its question and eliminated its own hypothesis: across a full build the child emitted no `ESC[r`, no `RIS`, no alternate-screen switch and no absolute cursor positioning, and the reservation reached the pty correctly (`rows=32 cols=118 reserve=1` on a 33-row terminal). Nothing scrolled over the bar, so `3.2.0-B3`'s fix is holding and the remaining explanations are both on sysforge's own side of the pty, where the dump cannot see: the region was released, or it was simply never repainted. Those are indistinguishable on screen and the logs record neither. Pointing `SYSFORGE_PROGRESS_TRACE` at a path appends a timestamped line for every `establish` (with the rows and the resulting region), `release`, `paint` (with the row and the text) and `sigwinch` — including the resize path's ignored case and the too-short-terminal skip, both of which leave no bar and no other trace. That separates the two in one run. Diagnostic only: it writes to a file and never to the terminal, is off unless the variable is set, and swallows every failure, since a diagnostic that can break the thing it observes is worse than none.

- **`3.2.0-F14` — the progress bar now shows elapsed time and an ETA.** The counter told you where a batch was but not how fast it was moving, so at default verbosity a healthy 40-second source sync and a stalled one looked identical — and a user who does not run with `-v` had no other channel to tell them apart. Every line painted inside a `tracker()` now carries a ` · <elapsed>` suffix and, once two items have finished, a ` · ~<eta> left` projection: `source sync · mesa · 1m04s · ~3m20s left`. The projection comes from **measured** per-item durations in the run you are watching, never from the configured per-operation timeouts — a timeout is a worst-case ceiling, so multiplying one by the item count would advertise an hour for a run that finishes in forty seconds, and the items already done were fetched on this machine, over this link, against this work. Three rules keep it from overstating, the same principle `build_estimate` already follows: nothing appears below a five-second floor, so a short batch looks exactly as it did before; the ETA waits for **two** completions, because one sample is not a rate; and an estimate that has been overrun is dropped rather than pinned at `~0s left`, since an item running long is stale information and not a finished one. The suffix is composed when the bar is painted rather than when an item ticks, so a whole package build sitting inside a single tick shows a clock that keeps moving instead of one frozen at the tick — the heartbeat repaint carries it. Applies to every batch that already had a bar (source sync, fetch, builds) with no new configuration and nothing to opt into.

## Changed

- **`3.2.0-F1` — the leaf layer no longer imports upward, and the guard now says so.** `tests/test_module_layering.py` banned `primitives/ -> pipeline.stages` imports, but the ban stopped at that one target and carried an allowlist of three exemptions, while 270 function-level imports across the package recorded cycles dodged rather than removed. Function-level deferral hides a cycle; it does not remove one, and the blast radius is real — `pipeline/stages/__init__.py` instantiates every stage at import, so a primitive reaching up for a single constant transitively pulls in every stage and everything they import. Three leaks are closed, each by relocation with a re-export left behind, so every existing import path and test patch point still resolves. **(a)** `resolve_state_dir` was a path computation living in `pipeline/state.py` that five primitives (`makepkg_wrapper`, `state_probe`, `source_sync`, `llvm_state`, `init_notice`) reached up for; it now lives in `primitives/paths.py` beside the XDG roots it already returns. **(b)** Seven primitives imported `sysforge.ui.progress` for the same five names — `suspend_for_prompt`, `suspended`, `reserved_rows`, `heartbeat`, `tracker` — none of which is a dependency on the bar: `primitives/progress_hooks.py` declares that surface as a protocol with a complete no-op default, and `ui/progress.py` registers itself as the implementation at import. Because the module object satisfies the protocol structurally there is no adapter to keep in sync, and a primitive now works with no UI layer present at all instead of importing a renderer, its `SIGWINCH` handler and its `atexit` hook to ask how many rows are reserved. **(c)** Live hardware detection moved down to `primitives/hardware_probe.py` (`detect_host_arch`, `parse_gpu_vendors`, `derive_llvm_targets`, `derive_mesa_drivers`), finishing what `2.6.1-F8` started when it moved only the mandatory-baseline tables, and the `BootstrapConfig` dataclass moved to `primitives/archinstall_config.py` where its principal consumer already lives — a shared shape, not a stage behaviour. With the three named leaks gone the guard widened from `sysforge.pipeline.stages` to `sysforge.pipeline` and `sysforge.ui` in full, which surfaced one remaining reach-up (`init_notice` reading `PipelineState`); it is pinned as the sole allowlist entry and filed as its own roadmap item. Pure relocation and dependency inversion — no behaviour change, and no user-visible change of any kind.

---

- **`3.2.0-F2` — the toolchain and kernel stages are packages, not 4263- and 2355-line modules.** `stages/toolchain.py` was the highest-risk file in the tree: four classes, thirty distinct sysforge imports and a 701-line `_build_llvm_pgo_inner`, with a 4945-line test file beside it. Its internal structure already named the seams as comment banners, so the split follows them rather than inventing a taxonomy — `constants`, `config`, `pkgbuilds`, `reuse`, `passes`, `profdata`, `verify`, `pgo`, `gates`, `identity`, `bolt`, and a `stage.py` that is sequencing only, delegating every step. `stages/kernel.py` is the same shape one size smaller and follows as `constants`, `config`, `source`, `fdo`, `kconfig`, `install`, `gates`, `stage`. Dependencies run one way in both, and each package's `__init__` re-exports every public name, so `sysforge.pipeline.stages.toolchain` and `.kernel` remain valid import paths and `stages/__init__.py`'s eager instantiation is untouched. Two conventions keep the split from decaying. Modules call each other **module-qualified** (`profdata.pgo_install(...)`, never a bare imported name), so a patch on the owning module is seen by every caller — without that, a split turns every seam into a name bound at import time that tests can no longer reach. And a name that **crosses a module boundary becomes public**: an underscore is a promise about one module's internals, and it stopped being true the moment another module needed the name. That rule is what the item's own success criterion measures, and the criterion is met decisively — private-patch sites into the toolchain stage fell from 84 to 1 (the survivor is a white-box unit test of `reuse._dep_versions_from_globals`, not a reach across a seam) and into the kernel stage from 25 to 0. Shared primitive seams (`prompt`, `pacman`, `primitives.config`) became module imports rather than name imports, so a test patches one point instead of one per stage module that happens to call them, and `TOOLCHAIN_PATH`/`KERNEL_PATH` each got a single home read by their siblings. The test files split along the same lines: whole-stage behaviour stays in `test_stage_toolchain.py`/`test_stage_kernel.py`, per-module unit tests move to `test_toolchain_<module>.py`, shared builders and the autouse gate-isolation fixture move to `tests/toolchain_helpers.py` rather than being copied per file, and seven tests covering `[stages.toolchain.result]` moved to `test_pipeline_state.py`, since what they exercise is that file's format rather than anything the stage does. Two latent bugs surfaced and are fixed: `kernel.py` was importing `toolchain._compiler_paths`, another stage's private, which now names the public `identity.compiler_paths`; and `write_kconfig_fragment`'s `config` parameter shadowed the sibling `config` module it calls for `pkgbuild_path`. Behaviour-preserving throughout, and verified as such rather than asserted: an AST comparison of every function against the original shows only `Name(x)` → `Attribute(Name(module), x)` rewrites, and every string constant in both packages is byte-identical to the original — a check that earned its keep by catching a module-qualification pass that had rewritten inside a string literal, turning the TOML key `capture_lsmod_snapshot` into `kconfig.capture_lsmod_snapshot`. No user-visible change of any kind.

- **`3.2.0-F5` — the run seam grew the shape its callers actually needed, and the toolchain's probes moved onto it.** `primitives/run.py` exists so that the unified run log, `--dry-run` and the throttle apply uniformly, yet raw `subprocess` calls kept reappearing across the tree — including the one behind the accelerator leak fixed as `3.2.0-B2`. The reason turned out to be a gap in the seam rather than carelessness at the call sites: `run.py` offered only `run_or_raise`, which raises on non-zero, and that is exactly wrong for a **probe**. When the question is "is `nm` installed?" or "what targets does this llvm-config report?", a non-zero exit and a missing binary are both *answers*; a seam that turns them into exceptions cannot be used, so every probe author correctly declined it and wrote a bare call — each with its own `try/except FileNotFoundError` and no entry in the run log at all, which is what made "why did sysforge decide that?" unanswerable from a log alone. `run.capture(cmd, **kwargs)` is that missing shape. It is argv-list only (standards row 17), captures text, and forces `check=False` so a caller cannot re-arm the raise by accident. A **missing binary returns `None`**, deliberately distinct from a command that ran and failed, which lets a caller tell "`nm` is not installed" from "`nm` found nothing" and replaces the hand-written `try/except` at every site — the kind of guard that is correct in nine places and forgotten in the tenth. Probes are logged at debug, so `-vvv` now shows them alongside the builds. The toolchain package's ten probes moved over (`pacman -Q`, `ldd`, `nm` twice, `clang --version`, `ld.lld --version`, `llvm-config`, `clang --print-runtime-dir`, `uname`, `readelf`), and their tests collapsed from a per-module `subprocess` patch to one patch of the seam itself. Four calls in that package stay raw on purpose and are the worked example of what `capture` does not cover: a `tar` extraction that must raise, a streaming privileged `pacman -U`, an `llvm-profdata` merge that needs its own `preexec_fn`, and `makepkg --packagelist`, which is a build invocation rather than a probe. Migrating the rest of the tree, and the ruff `banned-api` rule that fences `subprocess` once those batches are done, is tracked separately on the roadmap. No user-visible change.

---

- **`3.2.0-F6` — `toolchain.toml` and `kernel.toml` are parsed once, at stage entry, into frozen dataclasses.** The two stages carried 27 and 21 `cfg.get(...)` calls, so every default was re-derived at each read site and a mistyped key surfaced as a `None` deep inside a gate rather than as anything at stage entry. `ToolchainConfig.from_toml` and `KernelConfig.from_toml` are now the single place each file's raw dict becomes values the rest of the package uses. The hazard was not hypothetical: `compiler` fell back to `"gcc"` in the toolchain stage body and to `"llvm"` in Gate 1's sentinel, so a config with no `compiler` key would have run the GCC path while stamping its sentinel `"llvm"` — latent rather than live, since the GCC path returns before Gate 1, but it is exactly the failure the item exists to make impossible and it is now pinned by a test. Typing the fields surfaced two more: `rebuild_soname_consumers` is a three-valued mode (`"prompt"` | `"auto"` | `"off"`), not a flag, and is validated at parse time, so a typo warns instead of silently matching none of the gate's branches and taking the prompt path with nothing said; and `KernelConfig.compiler` is `str | None` rather than defaulted, because "unset" is load-bearing — it is the signal to fall through to the toolchain stage's result in pipeline state, and giving it a default would make a machine that built an LLVM toolchain silently compile its kernel with gcc. Frozen is the other half of the point: the kernel stage used to stamp its resolved `pkgbuild_src_dir` back into the config dict in place, and now rebinds to a `dataclasses.replace()` instance, so the value still reaches every downstream reader without anything holding the original seeing it change underneath. `raw` survives for exactly the consumers that take the whole table by design — `resolve_pgo_store`, `resolve_pkgbuild_src_dir`, and the Pass-4 reuse `config_digest`, which **must** keep hashing the raw table because hashing a field list instead would change every existing cache key and silently invalidate every user's reuse cache. The precedence-bearing resolvers stay functions, since `resolve_compiler` weighs a CLI flag against the TOML against pipeline state and `resolve_source` probes the filesystem — neither input is config. Schema validation now targets the dataclass rather than a parallel hand-maintained key set: `check_shipped`'s allowlist parity guard compares "keys the parse site reads" against the allowlist as an equality of sets, where the toolchain half used to be one-way containment plus a hand-maintained list of helper exemptions; both were verified to fail in both directions. TOML keys and file formats are unchanged — this is the in-process representation only, and there is no user-visible change.

- **`3.2.0-F8` — verb modules no longer import each other, and a guard keeps it that way.** `revert_cmd` and `uninstall_cmd` both pulled `cmd_state_forget` out of `state_cmd`; `build_cmd` reached into `packages_cmd` for the `packages.toml` writer. Each edge was defensible on its own, and together they were the seed of a fourth informal layer that nothing checked — DESIGN had asserted "no command module imports from another command module" for some time while three such imports were live. The direction of those edges was also arbitrary: nothing makes `state_cmd` the owner of "stop maintaining this package" except that `sysforge state forget` happens to be the verb that spells it. `verbs/shared.py` now holds cross-verb operations, so the *home* moves rather than the operation being duplicated — the one-home invariants (a single `packages.toml` writer, a single demotion path) are exactly what would have broken under a copy. Two clusters live there: the `packages.toml` entry shape and line-level writer (`OVERRIDE_FIELDS`, `entry_toml_block`, `entry_is_inert`, `rewrite_packages_toml` — no longer underscore-private, since it is now a deliberate cross-module call), and `forget_packages`. Relocating the latter fixed a smell the old filing had made invisible: two of its three callers were not the `forget` verb and were synthesising a fake `argparse.Namespace` to call a verb body as if it were an API. It now takes `(state_dir, pkgnames)` and returns `(forgotten, missing)`, leaving printing to the caller — `state forget` reports both lists, while `revert` and `uninstall` fold demotion into their own summaries — and `uninstall_cmd`'s `argparse` import fell out as dead. `state_cmd.cmd_state_forget` remains as the verb's thin argument-and-output adapter. `tests/test_module_layering.py` grew `test_verb_modules_do_not_import_siblings`, which counts function-level imports too, since deferring one dodges the load-time cycle without removing the dependency. Internal restructuring only — no user-visible change.

- **`3.2.0-F12` — the leaf layer's last upward import is gone, and the allowlist that held it is closed.** `3.2.0-F1` widened the layering guard from `sysforge.pipeline.stages` to `sysforge.pipeline` and `sysforge.ui` in full, and that widening surfaced exactly one remaining reach-up: `primitives/init_notice.py` imported `pipeline.state.PipelineState` to ask whether the `reconfigure` and `hardware` stages were done before printing the first-install advisory. Duplicating that read was never an option — `PipelineState` is the single home for `pipeline_state.toml`'s format, and a second parser is how two readers of one file drift apart — so the class moved down instead, to `primitives/pipeline_state.py`, the same shape `resolve_state_dir` and `hardware_probe` took in F1. The module was already a leaf in everything but filing: its only sysforge imports were `log` and `primitives.paths`. The two toolchain accessors travelled with it, since `get_toolchain_variant` and `get_toolchain_fingerprint` read the same file's `[stages.toolchain.result]` table and splitting them from the class would have re-split the home the move exists to keep whole. Relocating also retired a workaround: `get_toolchain_fingerprint` imported `build_fingerprint` and `config` lazily to dodge an import cycle via `pipeline` ← `build_core`, and that cycle existed only because of the old filing, so both are now ordinary module-level imports. `sysforge.pipeline.state` re-exports every public name for one cycle, so existing imports and the tests that patch names there are unaffected. With the move done `_ALLOWED_UPWARD_IMPORTS` is empty — and because the existing dead-entry check iterates that dict, an empty one makes it pass vacuously, so a second assertion (`test_layering_allowlist_is_empty`) now pins the door shut: re-authorising an upward import has to be a deliberate edit to a test that says so, not a one-line dict insertion. Pure relocation, one live call site, no behaviour change.

## Fixed

- **`3.0.0-B1` — the stage-owned update advisory now sees pinned repo checkouts.** `update._detect_stage_owned_updates` exists to say when a package it skipped (`owner_stage` set) has upstream movement waiting on `run toolchain` / `run kernel`. It resolved the candidate through `_check_one_pkgbase`, which for a `repo_class = "source"` entry compares the installed version against the version parsed from the **local** PKGBUILD. Stage-owned packages are excluded from the walk and therefore from source sync, so for a `source = "repo"` checkout that tree is a detached-HEAD pin which only ever advances inside the owning stage's own run: installed version and local PKGBUILD version are the same value by construction, the check could never yield `NEEDS_REBUILD`, and the advisory never fired — the one case the feature was built for. Observed live, with a toolchain package sitting three releases behind its repo version while the run printed only the `info`-level "skipping N toolchain-stage package(s)" line. Stage-owned `source = "repo"` entries now read the candidate from pacman's sync DB, which is the authority the pin itself targets and is offline-safe. The walk's exclusion and the pin's lifecycle are untouched — syncing stage-owned sources from `update` is exactly the double-processing the `owner_stage` skip exists to prevent. AUR-sourced stage-owned packages were unaffected and keep their RPC path. Advisory-only: no build or install behaviour changes.

- **`3.0.0-B5` — the ungated-source warning now fires on toolchain and kernel builds.** Under `--frozen`, sysforge does not mediate makepkg's own network, so it names the remote, uncached `source=()` entries the freeze cannot cover. That call was wired only into `build_core`'s per-target loop, and toolchain and kernel builds reach makepkg without passing through `build_core` — so a frozen run warned for ordinary packages and said nothing for precisely the builds where an unmediated fetch matters most: they run longest, pull the most code, and are the ones most likely left running unattended under `--frozen`. The gap was silent, since the freeze itself still held at all five gated seams; the user simply was not told what remained uncovered. The call moved up to `makepkg_wrapper.run()`, the one seam every build path crosses, rather than being duplicated per stage — a second call site would drift the way the frozen-exit check did before it was centralised. Advisory only; no enforcement change.

- **`3.1.0-B15` — an `AlreadyBuilt` exit no longer logs "Build failed" first.** makepkg exits 13 when a matching artifact is already in `PKGDEST`, and `build_core` classifies that correctly — it logs `<pkgbase>: package already built — installing existing artifact` and the run proceeds. But the wrapper's `finally` had already fired: it branched on a plain `success` boolean, and an `AlreadyBuilt` exit is not `success`, so it warned `Build failed — leaving patched PKGBUILD in place` one line earlier. The two adjacent lines contradicted each other and pointed the reader at the wrong package when the real failure was elsewhere in the batch. The verdict is now threaded into the `finally` on both retention paths, so it reports retention without the failure claim. Retention itself was already correct for this case — a rebuild at the same pkgver still needs the file — so only the message changed; every exit classification and the cleanup policy stay as they are.

- **`3.2.0-B1` — the build sandbox now builds the package instead of refusing it.** `[security] sandbox_builds` failed on *every* package, making the feature unusable as shipped. - **`3.2.0-B28` — a training-corpus build no longer applies the target's own saved PGO profile.** A plain rebuild re-applies a package's merged profile from an earlier `build <pkg> --pgo=use`, so a source-tracked package stays profiled. That reuse also fired for the toolchain corpus build, so mesa compiled with `-fprofile-use=…/pgo-mesa/mesa.profdata`, contrary to the invariant that corpus members are never `-fprofile-use` targets. A new `BuildOptions.pgo_reuse` field, threaded through `passes.build_pass`, gates the reuse, and the corpus pass sets it to false.

## Security

- **`3.0.0-B3` — a killed bootstrap no longer leaves the target with passwordless root.** The configure stage writes `/etc/sudoers.d/99-sysforge-bootstrap-build` granting the build user `NOPASSWD: ALL`, because `makepkg -s` must sync makedeps non-interactively while building sysforge inside the target. The `finally` that removes it covers exceptions and non-zero exits, but not `SIGKILL`, an OOM kill, or power loss mid-build — any of which left a freshly installed system carrying an unconditional passwordless-root rule for its primary user, in a file the user has no reason to look for. Low likelihood, maximum blast radius, and silent: the install looked incomplete rather than insecure. Two independent fixes, taken together. The rule is now scoped to `NOPASSWD: /usr/bin/pacman` — the one binary makepkg actually needs — so even a leaked drop is not root-equivalent; and stale `99-sysforge-bootstrap-*` drops are swept at bootstrap entry, so a `--resume` after a kill cleans up its predecessor. The sweep runs on the path that would otherwise re-create the file, since a `pre_check` refusal would block the very run capable of cleaning up.
