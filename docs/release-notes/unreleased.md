# sysforge (unreleased)

An opt-in build sandbox that runs PKGBUILD code in a clean container instead of as you, an `update --versions` report that answers "is anything newer?" without entering a stage, and a broad accuracy pass over build state, flag-drift visibility, sudo credential lifetime and dry-run output.

## Added

- **`3.1.0-F6` — `update --versions`: the available-version report, without entering a stage.** Answering "is there a newer toolchain or kernel?" previously meant either reading a full `update --dry-run` walk or entering `run toolchain` / `run kernel` itself. `sysforge update --versions` renders a `PACKAGE / INSTALLED / AVAILABLE` table and exits before the build loop, reusing the version check the walk already performed — it costs nothing beyond the check. Only actionable rows are listed (`NEEDS_REBUILD`, `NEEDS_PACMAN_UPGRADE`, `DOWNGRADE`); up-to-date packages collapse into a footer count, a failed check never occupies a row, and unresolved VCS packages become a single `--devel` hint rather than dozens of unknown-version rows. Stage-owned toolchain/kernel packages — which a normal run skips — are always included, annotated with the stage that owns them, sourced from the advisory path that carries that annotation. Mutually exclusive with `--explain-drift` (both are list-and-exit reports) and exempt from the stale-sentinel gate, on the same read-only grounds as `--dry-run`.

## Changed

- **`2.6.1-F29` — Colour-code the `update` version-check verdicts.** A `sysforge update --devel` run over a large `-git` set prints one summary line per package, and nothing distinguished the handful actually eligible to rebuild from the wall that were not — the reader parsed `NEEDS_REBUILD`/`UP_TO_DATE`/`DOWNGRADE` as text. The action tag now carries the verdict's colour: green for `NEEDS_REBUILD`/`NEEDS_PACMAN_UPGRADE`, yellow for the deliberate skips (`UP_TO_DATE`, `DEVEL`, `FROZEN`), red for `DOWNGRADE` and every failed check. The colour map is a second dict in `update_summary` keyed by the same action strings as `_ACTION_FORMATS` — a guard asserts the two key sets are equal, so a new action cannot land without one — and is applied through a new `color=` argument on `render.tag_header`, keeping the `[TAG]` gutter the one home for the shape and letting `log.use_color()` gate it for free; the padding is emitted outside the SGR run, so columns align on visible width. The gutter is the only correct surface here, and the reason is load-bearing: `log.info()` builds its file-log text from the caller's own message and only decorates level and tag for the terminal, so colour embedded in a *message body* is ungated and would land verbatim in `sysforge-update.log`. That invariant was unwritten and is now stated in `docs/design/12-logging.md` § Colour. One adjacent fix rides along: the `[VERSION]` `vercmp` line logged its two operands *before* comparing them, so the log stated a question and never answered it — it now reads `vercmp 'a' 'b' -> 1`.

## Fixed

- **`3.1.0-B1` — Record the version the build actually produced, not the oldest artifact in PKGDEST.** Build-state recording reverse-engineers `pkgver`/`pkgrel`/`epoch` from built `.pkg.tar.*` filenames, but took the *first* match a directory glob yielded. When `PKGDEST` is a shared, long-lived package archive holding every historical build (the common `/home/packages` layout), that first match is an arbitrary — in practice the oldest — version, so `build_state.toml` recorded a years-stale `pkgver` as "last built". The next run's `vercmp` then saw the on-disk PKGBUILD as newer, reported "upstream PKGBUILD has moved", and rebuilt the package again, indefinitely. Artifact selection now goes through `select_built_version()`, which considers only filenames parsing as the target pkgname and picks the most recently modified — the one the build that just finished produced. A local state file showed 69 affected packages.

---

- **`3.1.0-B2` — Stop advertising a drift-rebuild flag in the same run that already acted on it.** The toolchain- and flag-drift advisories printed "Pass `--rebuild-on-toolchain-drift`/`--rebuild-on-flag-drift` to rebuild" unconditionally whenever drift was detected, including when that rebuild was already enabled via the flag, the per-axis `[update]` key, or the `rebuild_on_drift` umbrella. A run would emit the "pass this flag" hint immediately above "promoted 26 UP_TO_DATE package(s) to NEEDS_REBUILD", making legitimate same-version rebuilds read as spurious reinstalls. The drift axes are now resolved before the advisories, which report `rebuilding (--rebuild-on-flag-drift)` when the rebuild is already in effect and keep the opt-in hint only when it is not.

---

- **`3.1.0-B3` — Stop pinning repo checkouts to a superseded release when the local sync DB is stale.** `SourceSyncScheduler._pin_repo_checkout` resolved the release tag to check out via `pacman.get_pacman_sync_version`, which reads `/var/lib/pacman/sync/*.db` through pyalpm or `pacman -Si` — neither touches the network. On a rolling repo that means the "available" version is whatever the last `pacman -Sy` left on disk, so a sync DB even a few hours old pins an already-superseded release; the kernel stage reported 7.1.8 as the newest available while the repos carried 7.1.9. The pin now resolves through a new `pacman.get_repo_candidate_version`, which cross-checks the sync DB against `checkupdates_map()` — `checkupdates` refreshes a *side copy* of the sync DBs, so it needs no sudo and cannot leave a partial-upgrade state — and takes whichever version is newer by `vercmp`. It is a strict enrichment: an absent `checkupdates` entry, an unavailable tool, or an older value all fall back to the previous sync-DB answer, and the probe is memoized for the process so one run covers every pinned package. Applies to all `source = "repo"` pins, not just the kernel.

---

- **`3.1.0-B4` — A timed-out sudo prompt at kernel-install time no longer strands a recovery sentinel.** The kernel stage opens `sentinel_scope` around the install → mkinitcpio → bootloader mutation window, and the first thing inside it is `install_built_packages`, which runs `sudo pacman -U` with inherited stdio. Leave a multi-hour build unattended and sudo's `passwd_timeout` fires, so **sudo exits non-zero without ever exec'ing pacman** — nothing installed, no file on the system touched. That was indistinguishable from a genuine pacman failure: it raised out of the scope, and by the sentinel contract any exception leaves the record in place, so the next invocation demanded the recorded recovery command. The operator had to run a pointless `mkinitcpio` to clear a sentinel guarding a mutation that never began. The stage now acquires credentials *before* entering the scope, via the `sudo -v` auth probe (out of scope for the privilege seam by that module's own docstring), and on failure aborts cleanly with a message saying nothing was installed and naming the plain re-run — no sentinel written, no recovery ritual. The classification stays deliberately narrow: only a pre-install auth failure is a clean abort; a `pacman -U` that actually ran and failed still leaves the sentinel behind, which is the unbootable-system case it exists for. Pairs with `3.1.0-B5`, which stops the prompt from going stale in the first place; this is the safety net for when it still does.

---

- **`3.1.0-B5` — Give the kernel stage the same sudo keepalive the toolchain stage has, so its final install prompt cannot go stale.** The toolchain stage runs a background thread refreshing `sudo -v` throughout its 2+ hour PGO sequence, precisely so the install at the end does not re-prompt an operator who has walked away. The kernel stage builds for just as long and installs the same way — `install_built_packages` calling sudo directly from the sysforge process, so the same timestamp entry applies — but had no equivalent: credentials authenticated at stage entry were long expired by the time the build finished, and the run stopped on a password prompt that then timed out. How routinely this bites is visible in `makepkg_invoke`, which carries a whole interactive "build likely succeeded but install failed (sudo timeout?)" recovery path that the kernel stage's split build/install shape bypasses entirely. Rather than copy the daemon, it moved to a new `primitives/sudo_session.py` — the one home for credential *lifetime*, distinct from `primitives/privilege.py`, which owns *escalation* and explicitly puts auth probes out of scope. It exposes `authenticate()` (returns whether credentials are usable, so a caller can tell "not authorized, nothing happened" from "ran and failed" — this is what `3.1.0-B4` branches on) and a `keepalive()` context manager that always stops and joins its daemon on exit, including on exception, so a stage cannot leak one by forgetting its teardown. Both long-building stages now use it. Callers must authenticate before entering the keepalive, since the refresh inherits stdio and would otherwise prompt from a background thread; the daemon itself remains best-effort and non-fatal, warning on a failed refresh exactly as before.

---

- **`3.1.0-B6` — Stop forcing maximum verbosity on every `--dry-run`.** `log.set_dry_run_mode()` set `_VERBOSITY = 3` unconditionally, and `cli.main` called it *after* resolving the user's verbosity — so `--dry-run` overrode `-v`, the `[log] verbosity` config key, and even `--quiet`. A dry-run on a 190-package install emitted 2249 lines, 1701 of them `[DEBUG]` profile dumps, burying a six-line answer. The forcing predates the `ui()` level, when max verbosity was the only way a dry-run printed anything; it is now removed, and `set_dry_run_mode()` only redirects output to stdout (which was always correct). Four dry-run *verdicts* whose real-run counterparts raise — the kernel stage's fallback-kernel and `/boot`-space aborts, and the toolchain stage's Gate 1 findings — were emitted at `warn()` and would have gone silent at the shipped default; they are re-levelled to `ui()`, matching the rubric's existing "dry-run previews are `ui()`" rule. The regression guard drives the real `cli._main()`: the existing `quiet_at_default` fixture reimplements the dispatch order it is meant to guard, applying verbosity *around* `set_dry_run_mode()` where production applies it *before*, which is why this was invisible to it.

---

- **`3.1.0-B7` — `--dry-run` no longer forces the progress bar into plain mode.** `ui/progress._detect_mode` returned `"plain"` whenever `log._DRY_RUN` was set, alongside the genuine non-interactive cases, and plain mode emits a discrete line per step instead of one rewriting line — so a dry run over a 110-package source sync printed ~300 progress lines on an ordinary TTY, which was the entire remaining bulk of `sysforge --quiet update --dry-run` (whose non-progress output is nine lines). The rung looked like a deliberate pairing with the other half of `set_dry_run_mode`, which redirects log output to stdout: avoiding ANSI cursor control interleaved with the report is a real concern, but it does not apply, because progress writes to **stderr** — the two are on separate descriptors and cannot interleave. The rung is removed; the remaining four already cover every case where plain output is genuinely required, including the piped-to-a-file shape a scripted dry run actually takes. A second, subtler coupling went with it: the colour rung asked `log.use_color()`, which follows `log._out()` — and `_out()` swings to stdout under `--dry-run`, so a redirected stdout dragged progress back into plain mode one rung later. `use_color()` now takes an optional stream, and progress passes `sys.stderr` explicitly, so the mode/env precedence stays in its single home while the decision is made about the descriptor progress actually writes to. Follows `3.1.0-B6`, which removed the same function's verbosity forcing; this was the last behaviour still keyed off `_DRY_RUN` beyond the stdout redirect it exists for.

---

- **`3.1.0-B8` — Keep the distro's compiler hardening flags across a profile `CFLAGS` override.** `emit_makepkg_conf` merges `/etc/makepkg.conf` with the resolved profile *per key*, not per token, and the shipped `standard` and `optimized` profiles set `CFLAGS` in full — so every package built through them compiled without `-Wp,-D_FORTIFY_SOURCE=3`, `-fstack-protector-strong`, `-Werror=format-security` or `-fexceptions`, losing run-time buffer-overflow detection, the stack-smashing protector and format-string rejection that the system conf applies by default. That this was an oversight rather than a policy choice is visible in the same profiles' `LDFLAGS`, which carefully keep `-z,relro,-z,now` — the *linker* half of the same hardening set. A new `[preserved_system_tokens]` table in `profiles.toml` declares, per conf key, which tokens of the system value survive an override; they are re-added by `profile.merge_preserved_tokens` with profile-wins precedence — a profile that already names the token, names a conflicting one in the same `[append_conflict_groups]` group (`-fno-stack-protector`), or names one in the same flag family (`-Wp,-D_FORTIFY_SOURCE=2`) keeps its own value, so opting out stays possible and explicit. Only tokens the system conf actually sets are restored, so nothing is invented on a distro that omits them; `CXXFLAGS = "$CFLAGS"` inherits by shell expansion rather than injection; kernel builds are unaffected (their flag keys already pass through verbatim). A profile can opt out of the pass entirely with `preserve_system_tokens = false`.

- **`3.1.0-B9` — Keep shipped section order when `sync-config` injects a table, so a relocated section can't read as a deleted one.** `sync_config.merge_container` appended every newly-injected table to the *end* of the live file rather than to the position it holds in the shipped default. TOML ignores section order, so the resolved config stayed correct and the defect was invisible at runtime — but the live file's layout diverged from shipped a little further with every sync, and the `.sfnew` adoption step is a line-based `difflib` diff with no move detection. A section sitting at a different offset in the two files therefore renders as a deletion in one hunk and an addition hundreds of lines away in another; read top-down that says "this section is missing from the shipped file", and hand-merging against that reading deletes a live section for real. On a local config this cost `profiles.toml` its entire `[consumes_inference]` table. A new table is now spliced after its nearest shipped-order predecessor that the live file actually has — falling back through the shipped order, and to EOF only when there is no such predecessor — so an already-reordered live file still anchors against a real neighbour, and a run of consecutive new tables stays in shipped order by anchoring on each other. Insertion lands immediately after the anchor's own entry, before any standalone comment run tomlkit holds for the following table, so those comments stay attached to what they document; the write remains idempotent. Defence in depth at the reading end: `config_cmd._diff_text` now prepends a banner naming any section header the diff shows as both removed and added, since a header on both a `-` and a `+` line is present in both files. Pre-existing order drift in a live file is not rewritten — the tool never does a wholesale rewrite of a config it did not lay out.

- **`3.1.0-B10` — Release the progress bar's reserved terminal row before handing a full-screen editor the tty.** `editor.run_tty_argv` — the one home every editor and merge-tool launch goes through — bound the child to `/dev/tty` but left `ui.progress`'s DECSTBM scroll region (`ESC[1;N-1r`) in place. A verb can hold an active bar when it reaches an edit prompt: the build-failure recovery menu's `[e]` opens the PKGBUILD from inside `update`'s `"building"` tracker, and `config merge`, `artifact edit` and the reconfigure stage can all do the same. The editor sizes itself to the full terminal and paints its own status line onto the row the bar has reserved, so the two fight over it and the bottom line is left corrupted after the editor exits. The child now runs inside `progress.suspended()`, which fully releases the region and repaints the bar on return — the same contract `maybe_pager` already relied on for the identical pager corruption (B5), and `invoke_makepkg` for makepkg's own cursor-addressing children via `reserve_bottom_rows`. Fixing it at the shared launcher covers every caller at once; the guard asserts the suspend brackets the subprocess call.

- **`3.1.0-B11` — Compare the *effective* flags for drift, so the hardening-preservation pass can't change every build unnoticed.** `3.1.0-B8` re-adds the distro's compiler hardening tokens at the conf-emission seam, after profile resolution — but `flags_string` in `build_state.toml` was written from `profile.serialize_flags(resolved_profile)`, the *pre-merge* profile, and `flag_drift.resolve_flag_drift` re-resolved the same pre-merge string to diff against it. Both sides of the diff therefore ignored the pass entirely: shipping B8 changed what every future build compiles with, and not one installed package was reported as drifted, so nothing was ever rebuilt with the restored hardening. The same blind spot covered any change to `[preserved_system_tokens]`, to `[append_conflict_groups]`, or to `/etc/makepkg.conf`'s own hardening baseline — a whole class of flag change the canonical flag-drift surface could not see. The pass now has one implementation, `profile.apply_preserved_system_tokens`, called by both seams: `emit_makepkg_conf` for the conf the build reads, and a new `makepkg_conf.serialize_effective_flags` for the string the record site writes and the drift site re-resolves, so the two cannot diverge again. Both take the same `kernel_build` verdict (`build_mode == "kernel" or owner_stage == "kernel"`, replayable because `owner_stage` is persisted), so a stage-owned kernel build does not drift against itself, and `preserve_system_tokens = false` still short-circuits the pass. Recorded flags now track `/etc/makepkg.conf`, which is deliberate: a distro update that weakens or widens the hardening baseline is real drift. Existing entries were all recorded pre-merge, so the first `sysforge update` after this change reports every source-built package as flag-drifted — that report is accurate, and `--rebuild-on-flag-drift` is what re-hardens them.

- **`3.1.0-B13` — Isolate `SYSFORGE_STATE_DIR` for every test, so the suite cannot write to a real `build_state.toml`.** `tests/conftest.py` offered a `state_dir` fixture that redirects the state dir, but only for tests that asked for one; everything else inherited the developer's ambient `SYSFORGE_STATE_DIR` and wrote to their live state file. A test does not have to be *about* build state to do it — `test_run_profile_override_kernel_derives_kernel_build` patches `_run_build`, but `makepkg_wrapper.run` still falls through to `_record_build_state`, which stamped a `linux-unruled` entry (`pkgbuild_dir` pointing into `/tmp/pytest-of-*`, `owner_stage = "kernel"`) into the live file. The result is a phantom package that reports as a drifted, source-built, kernel-owned entry on every `sysforge update`, offers itself for rebuild against a `pkgbuild_dir` that no longer exists, and cannot be cleaned up automatically: stage-owned entries are exempt from `reconcile_external_installs`' demotion, and the superset sync keeps rather than prunes it. A new `_isolate_state_dir` autouse fixture now points the variable at a throwaway tree for every test, mirroring `_isolate_local_pacman_db`; the opt-in `state_dir` fixture still wins for tests that request it. `tests/test_state_dir_isolation.py` pins the guarantee itself — including the exact patched-`_run_build` shape that leaked — so removing the fixture fails a test rather than silently resuming writes to a user's home.

- **`3.1.0-B14` — Let the just-in-time install break a stale exact-version pin held by a package the same batch is about to rebuild.** A `lib32-*` VCS package typically pins its 64-bit sibling by exact version (`depends=("egl-wayland-git=$pkgver")`), and that pin makes the pair unupgradable one at a time: pacman refuses to install the new `egl-wayland-git` while the *installed* `lib32-egl-wayland-git` still requires the old version, and the only package that would satisfy the new pin is the lib32 artifact this run has not built yet — no single transaction is valid. The intra-batch ordering and just-in-time install (shipped in v2.0.0) both did their jobs (the sibling was built first and handed to `install_built` before the dependent's makepkg call), but the `pacman -U` underneath was refused, so the dependent then configured against the stale installed version and makepkg aborted with exit 8. The just-in-time path now passes `allow_break_deps` — the `pkgname`s of every batch member not yet built, the target being built included, since it is the usual pin holder — to `pacman.batch_install_pkgs`, which confirms via a new `deps_broken_by_install` dry run (`pacman -U --print`: unprivileged and side-effect free, so asking costs no sudo prompt) that the breakage is confined to that set before adding a **single** `--nodeps`. One `--nodeps` skips dependency *version* checks only, which is exactly the pin's failure mode — the package name is still provided — so a genuinely absent dependency still aborts the transaction; `-dd` was deliberately not used. Breakage held by anything outside the batch warns and leaves enforcement fully on. Correctness rests on the holders being rebuilt and reinstalled later in the same run, which restores consistency at the final bulk install. A diagnosability fix rides along: an interactive `pacman -U` inherits its streams so the conflict prompt works, which meant its refusal reached the terminal and never the unified run-log — the log ended at a bare "Batch package install failed" with the reason nowhere in it, which is what made this failure hard to read. The exit status and a pointer to the terminal are now logged.

---

- **`3.1.0-B16` — Read both of pacman's streams when probing for broken dependencies, so `3.1.0-B14` actually fires.** `deps_broken_by_install` captured only stderr from its `pacman -U --print` dry run, but pacman splits a transaction-preparation refusal across both streams: the generic `error: failed to prepare transaction (could not satisfy dependencies)` header goes to stderr, while the `:: installing X (v) breaks dependency 'D' required by Y` line — the only part naming the dependency and its holder — goes to **stdout**. The probe therefore returned `{}` for every refusal, however severe, and since an empty result means "no known breakage" (the deliberate fail-closed contract), `batch_install_pkgs` never added `--nodeps` and B14 was inert: the `lib32-egl-wayland-git` / `egl-wayland-git` pair still deadlocked with the same makepkg exit 8. The probe now captures and scans both streams. The defect survived review because the manual reproduction that characterised the error used `2>&1`, which merges the streams and hides which one carries what, and the unit test was then written from that merged transcript — so it asserted against a stderr payload real pacman never produces and passed against broken code. The regression test now feeds stdout and stderr separately, and the fix was confirmed against the live deadlocked system rather than mocks alone. The same stream split explains why the non-interactive install relay logs only the header: pacman's detail lines go to inherited stdout, reaching the terminal but not the unified run-log. That is left as is — capturing stdout there would silence pacman's live progress output during installs — and the pre-install probe now logs the breakage explicitly on the path where it matters.

## Security

- **`3.1.0-F7` — Opt-in build sandbox: run PKGBUILD code in a clean container instead of as you.** A PKGBUILD's `prepare()`/`build()`/`package()` are arbitrary code, and every build ran unsandboxed on the host: `~/.ssh`, GPG material and browser profiles were readable at build time, which is the actual execution vector of the AUR supply-chain campaigns — the payload runs during the build and never has to land in a package at all. `[security]` previously offered only `freeze_sources`, which gates code *ingress*; there was no lever for blast *radius*. New `[security] sandbox_builds` (default `false`) replaces the makepkg invocation with a `makechrootpkg` one, so the build executes inside a clean `systemd-nspawn` container as an unprivileged `builduser` with only the PKGBUILD directory bind-mounted; `sandbox_chroot_dir`, `sandbox_clean` and `sandbox_update` tune the chroot, and a profile can override the switch either way with `sandbox_builds` in `profiles.toml`. The argv *shape* branches rather than composing another throttle prefix, because `makechrootpkg` works on the current directory, cannot honour `-p <name>`, and escalates itself — so a `sudo` of ours would strip its preserved `PKGDEST`/`SRCDEST`/`LOGDEST` and relocate every artifact. Four collaborators move with it: the dest variables are exported from the emitted conf so artifacts land exactly where the host path leaves them; a container-side conf is derived with the dest keys repointed and the env-delivered `CC`/`CXX` re-added as `export` lines (the invocation env does not cross the boundary); `[build] mem_limit`'s `RLIMIT_AS` clamp is dropped with a warning rather than silently capping the wrapper instead of the build; and dependencies built earlier in the run — installed on the host, invisible to the container — are fed back in as `makechrootpkg -I` through a session artifact registry. Preflight refuses rather than downgrades: a missing `devtools`, a missing `<chroot>/root`, or a non-`PKGBUILD` filename each stop the build with the command that fixes it, because a security opt-in that silently falls back to the host hands the user exactly the exposure they opted out of. `run toolchain` and `run kernel` are exempt — both build against, and install into, the host they are upgrading. Rejected alternative: adding `ProtectHome=`/`PrivateTmp=` to the existing `systemd-run --scope` wrapper, which cannot work — `--scope` never execs the command, so systemd rejects exec properties outright. Known scope limit, documented in README and DESIGN and tracked in ROADMAP: the container resolves build deps from the stock repos rather than the host's installed set, so a dependency built in an *earlier* run is not visible to it, and a source-built package ahead of the repos is replaced by the repo version — which is why the feature is scoped at untrusted AUR leaf packages whose deps come from repos. The optimization of the host's own packages is not affected: it lives in their installed binaries, which the built package still runs against.
