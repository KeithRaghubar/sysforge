## Added

- **`2.5.1-F3` — `state failed --clear-all` now emits a `SYSFORGE_TARGET`.** Follow-up to `2.4.0-F1`, which gave every sentinel-gated verb a `journal_target` override. `StateFailedVerb.journal_target` keyed only on `args.clear`, so a `--clear-all` invocation — equally sentinel-gated, since it rewrites `build_state.toml` — fell to `None` and journalled the verb name alone. It was the one spot where 2.4.0-F1's "every mutating verb supplies a meaningful target" goal was not met, which meant `journalctl SYSFORGE_VERB=state-failed` could not distinguish "wiped every recorded failure" from "cleared one package". The clear-all path now emits the subjectless `mode:failed-clear-all` target; `--clear` still wins when both are set, since a named subject is more useful. Observability only — no correctness impact.

---

- **`2.6.1-F28` — `artifact review --all` bulk-adopts every offerable candidate.** Adoption was one-file-at-a-time: `artifacts.adopt` takes a single `src`, reached only through a per-candidate prompt loop, so pointing sysforge at a directory that is already a curated set — a `~/.local/bin` that has accumulated dozens of hand-written scripts — cost one keystroke per file. `--all` iterates the *same* `iter_offerable(registry, ignore)` result the interactive loop walks, which is the whole point: the exclusion rules (package-owned, sysforge-owned, already-managed, declined-and-unchanged) keep a single home and cannot drift between the interactive and bulk paths. It skips candidates whose ownership pacman could not determine unless `--include-unknown` is also given — an unknown owner means the file may in fact be package-owned, and a blind bulk adopt is exactly where that mislabel does damage — respects the ignore list as the interactive loop does, since a recorded decline is a decision, and runs off a TTY, replacing the list-and-hint branch when the flag is given. A per-candidate failure logs and continues, and the run closes with an adopted/skipped/failed count. Low risk by construction: adoption is copy-only, touches no live file, and is undone by `artifact remove --purge`.

---

- **`3.0.0-F5` — Itemize the flag-triggered `pacman -Syu` in the update summary.** Phase 6.5 has two routes into the same transaction, and only the classified one could report what it did: a `--sysupgrade` / `[build] system_upgrade` run hands the whole transaction to pacman, so the summary knew only that it had happened and printed `system upgrade (pacman resolved the transaction)`. That was honest but strictly less useful than a hand-run `-Syu`, and it was the common case — the managed set rarely holds `build_mode = "pacman"` entries, so the classified list is usually empty precisely when the flag route fires. The block now itemizes `pkg: old → new` for the requested-upgrade route too, from a reporting-only capture that snapshots the local package DB either side of the transaction and diffs the pair (`pacman.diff_installed`). Reading the DB *back* is the point: it reports what pacman actually did rather than what a second resolver predicted, and it needs no `checkupdates` probe — which is what decoupling the flag route removed in the first place. Fresh installs render `(new) <ver>` and removals `<ver> (removed)`. Output is scaled by verbosity, because a stock `-Syu` can be hundreds of packages unlike the bounded managed list: the default view caps the block and closes with `... and N more (-v for the full list)`, `-v` and above print it in full. The capture is on by default, applies only to the requested-upgrade route, and is turned off with `--no-sysupgrade-report`; it is best-effort throughout, so a failed snapshot drops the report and never the run, falling back to the existing single line.

- **`3.1.0-F5` — the first `run toolchain` / `run kernel` on an install now points at the config that drives it.** These are the two stages whose behaviour is decided almost entirely by their TOML rather than by the flags the user typed — `toolchain.toml` picks the compiler and the PGO passes, `kernel.toml` picks the kconfig fragments and initramfs handling — so a user who ran `setup` and then typed `sysforge run kernel` got a kernel built from defaults they had never opened. The existing first-install advisory could not cover this: it keys on the marker the `post_install` scriptlet drops and retires itself the moment `reconfigure` and `hardware` are both done, i.e. it clears *before* anyone reaches toolchain or kernel. `init_notice.maybe_emit_stage_config_notice` now names the config file and the two or three settings most likely to surprise, on both pipeline entry points. "First run" means never *completed*, not never *attempted*, so a failed first attempt re-advises — the config is exactly as unread as it was before, and a failed stage is the one most likely to be retried blind. No new state is needed: `PipelineState.stage_status` already returns `"pending"` for a stage it has never seen. Strictly advisory — it prints, never prompts, never blocks, and never raises.

- **`3.1.0-F9` — a sandboxed build now sees the dependencies you built in earlier runs.** `arch-nspawn` gives the container its own `/etc/pacman.conf`, so `makechrootpkg --syncdeps` resolves build deps from the stock repos and never from the host's installed set. The session registry already fed back packages built *in the same run*, which is why an `update` across a stack resolved — but a one-off `sysforge build cosmic-comp-git` whose `cosmic-protocols-git` was built last week got `error: target not found`, because that dependency exists only as an installed host package. The whole self-built stack was out of the sandbox's reach, which is why the feature was documented as scoped at AUR leaf packages. `build_state.toml` turned out to already carry the right shape to seed from: it is keyed by **pkgname** rather than pkgbase, so split packages arrive pre-expanded, which is exactly what `-I` needs since it takes package *files*. `resolve_dep_artifacts` scopes the injection to the target's dependency closure ∩ source-built — not every source-built package, which on a stack machine is ~150 files copied into the working copy and installed in one `pacman -U` per build — walking the closure over the host's local DB in a single pass, since `build_state` records versions but no dependency edges. Version selection is the part that matters most: the artifact matching what the host *currently runs*, never the newest file in `PKGDEST`, because that directory is a long-lived archive of every historical build (`3.1.0-B1`) and injecting its newest would hand the container a version the host does not have, recreating the very skew the injection removes. That matcher was lifted out of `build_core._find_existing_artifacts` into `makepkg_artifacts.find_artifacts` with a new exact-version mode — `primitives/` cannot import from `build_core`, and a second copy would have drifted — with `build_core` keeping the old name as a delegate. A source-built dep whose artifact was pruned from the archive warns, naming the package and the version being substituted, and continues: the container falls back to the repo version, which is a build-fidelity mismatch rather than a breach of the isolation boundary, and unlike the sandbox's refuse-rather-than-downgrade preflight there is no matching risk to justify a hard stop over a pruned file. `install_args` unions the two sources with the session registry winning, since this run's own builds are newer than anything the store points at. Does **not** fix version skew against packages outside the injection set — a source-built package ahead of `extra` is still replaced in the container by the repo version. That class needs a local pacman repo named in the chroot's own `pacman.conf` and remains open on the roadmap.

- **`3.2.0-B9` — a `SYSFORGE_PTY_RAW_DUMP` capture for diagnosing terminal-state bugs.** The bottom progress bar still disappears for the length of some builds after `3.2.0-B3`, and the existing record cannot answer why: `run_with_pty` relays the child's bytes to a `line_callback` whose consumers run them through `strip_ansi` before anything is written, so the log holds only the visible text. The sequences under suspicion — a DECSTBM reset, `RIS`, an alternate-screen switch, any of which would end the bar's scroll region for the rest of the run — are precisely the ones that filter removes, which means scanning the log for them returns zero whether they were emitted or not. Pointing `SYSFORGE_PTY_RAW_DUMP` at a path appends the child's stream verbatim, before any filtering, and leads the file with the winsize actually handed to the pty (`rows`, `cols`, `reserve`) — the second half of the question, since B3's fix turns on the reservation surviving `makechrootpkg -> sudo -> arch-nspawn -> systemd-nspawn` and a lost reservation and a reset region produce the same symptom. Off unless the variable is set, and best-effort at every step: an unwritable path, a failed write and a failed close are each swallowed, so a diagnostic can never be the reason a build stops. Diagnostic only — it observes the stream and changes nothing about it.

---

- **`3.2.0-B11` — a `SYSFORGE_PROGRESS_TRACE` record of the bar's scroll-region transitions.** `3.2.0-B9`'s raw pty dump answered its question and eliminated its own hypothesis: across a full build the child emitted no `ESC[r`, no `RIS`, no alternate-screen switch and no absolute cursor positioning, and the reservation reached the pty correctly (`rows=32 cols=118 reserve=1` on a 33-row terminal). Nothing scrolled over the bar, so `3.2.0-B3`'s fix is holding and the remaining explanations are both on sysforge's own side of the pty, where the dump cannot see: the region was released, or it was simply never repainted. Those are indistinguishable on screen and the logs record neither. Pointing `SYSFORGE_PROGRESS_TRACE` at a path appends a timestamped line for every `establish` (with the rows and the resulting region), `release`, `paint` (with the row and the text) and `sigwinch` — including the resize path's ignored case and the too-short-terminal skip, both of which leave no bar and no other trace. That separates the two in one run. Diagnostic only: it writes to a file and never to the terminal, is off unless the variable is set, and swallows every failure, since a diagnostic that can break the thing it observes is worse than none.

## Fixed

- **`3.0.0-B1` — the stage-owned update advisory now sees pinned repo checkouts.** `update._detect_stage_owned_updates` exists to say when a package it skipped (`owner_stage` set) has upstream movement waiting on `run toolchain` / `run kernel`. It resolved the candidate through `_check_one_pkgbase`, which for a `repo_class = "source"` entry compares the installed version against the version parsed from the **local** PKGBUILD. Stage-owned packages are excluded from the walk and therefore from source sync, so for a `source = "repo"` checkout that tree is a detached-HEAD pin which only ever advances inside the owning stage's own run: installed version and local PKGBUILD version are the same value by construction, the check could never yield `NEEDS_REBUILD`, and the advisory never fired — the one case the feature was built for. Observed live, with a toolchain package sitting three releases behind its repo version while the run printed only the `info`-level "skipping N toolchain-stage package(s)" line. Stage-owned `source = "repo"` entries now read the candidate from pacman's sync DB, which is the authority the pin itself targets and is offline-safe. The walk's exclusion and the pin's lifecycle are untouched — syncing stage-owned sources from `update` is exactly the double-processing the `owner_stage` skip exists to prevent. AUR-sourced stage-owned packages were unaffected and keep their RPC path. Advisory-only: no build or install behaviour changes.

- **`3.0.0-B5` — the ungated-source warning now fires on toolchain and kernel builds.** Under `--frozen`, sysforge does not mediate makepkg's own network, so it names the remote, uncached `source=()` entries the freeze cannot cover. That call was wired only into `build_core`'s per-target loop, and toolchain and kernel builds reach makepkg without passing through `build_core` — so a frozen run warned for ordinary packages and said nothing for precisely the builds where an unmediated fetch matters most: they run longest, pull the most code, and are the ones most likely left running unattended under `--frozen`. The gap was silent, since the freeze itself still held at all five gated seams; the user simply was not told what remained uncovered. The call moved up to `makepkg_wrapper.run()`, the one seam every build path crosses, rather than being duplicated per stage — a second call site would drift the way the frozen-exit check did before it was centralised. Advisory only; no enforcement change.

- **`3.1.0-B15` — an `AlreadyBuilt` exit no longer logs "Build failed" first.** makepkg exits 13 when a matching artifact is already in `PKGDEST`, and `build_core` classifies that correctly — it logs `<pkgbase>: package already built — installing existing artifact` and the run proceeds. But the wrapper's `finally` had already fired: it branched on a plain `success` boolean, and an `AlreadyBuilt` exit is not `success`, so it warned `Build failed — leaving patched PKGBUILD in place` one line earlier. The two adjacent lines contradicted each other and pointed the reader at the wrong package when the real failure was elsewhere in the batch. The verdict is now threaded into the `finally` on both retention paths, so it reports retention without the failure claim. Retention itself was already correct for this case — a rebuild at the same pkgver still needs the file — so only the message changed; every exit classification and the cleanup policy stay as they are.

- **`3.2.0-B1` — the build sandbox now builds the package instead of refusing it.** `[security] sandbox_builds` failed on *every* package, making the feature unusable as shipped. Two correct invariants had never been composed: `makechrootpkg` bind-mounts the invocation directory and hardcodes `source PKGBUILD` for its pkgbase probe, so it can only build that exact filename — while sysforge never builds the upstream file at all, since every route through `makepkg_wrapper._run_build` reassigns the path to the patched `PKGBUILD.sysforge` sidecar (which is why the host path passes `makepkg -p <name>`). `preflight` refused any non-canonical filename to avoid building one file and reporting another, so it refused the only filename the pipeline ever produces. The refusal is fatal by design — `SandboxUnavailable` is never downgraded to a host build — so the result was a hard stop on every target rather than a silent weakening. `build_sandbox.as_canonical_pkgbuild` now reconciles the two with a scoped rename around the build: the upstream file is parked at `.sysforge-upstream-PKGBUILD`, the sidecar occupies `PKGBUILD` for the container's benefit, and both names are restored in the same `finally` that removes the scratch conf — on the success, failure and exception paths alike. A rename in place rather than a staged copy elsewhere, because the build also needs that directory's local sources, `.install` scripts, patches and keys, and replicating that set is the larger surface to get wrong. The filename check is replaced, not dropped: a `.sysforge-upstream-PKGBUILD` left behind by an interrupted run is now itself a refusal in both `preflight` and the swap, since completing a second swap over it would replace the user's upstream PKGBUILD with a patched one permanently. The escape was a test-fixture artifact — every sandbox test fed the seam a bare `PKGBUILD`, a filename production never generates — so the suite now drives the seam with a realistic upstream/sidecar pair and asserts the checkout is byte-identical afterwards.

- **`3.2.0-B2` — host-only build accelerators no longer fail every sandboxed build.** With `3.2.0-B1` clearing the preflight refusal, `[security] sandbox_builds` reached `makechrootpkg` for the first time and then failed all nine packages of an `update` run at an identical point, before `prepare()`: `==> ERROR: Cannot find the ccache binary required for compiler cache usage`. `chroot_conf_text` derives the container conf by copying the emitted host one and appending, so `BUILDENV=(!distcc color ccache !check !sign)` rode along verbatim into a chroot that is `base-devel` only — and makepkg treats a missing accelerator as a hard error, not a downgrade, so the build died in seconds regardless of what it was building. The module already understood that host *paths* are wrong inside the container (`_CHROOT_DEST_KEYS`, `_ENV_EXPORT_DENY`); it had never extended that reasoning to host *binaries*, which arrive through two separate channels. `_container_buildenv` now negates `ccache`/`distcc` in the emitted `BUILDENV` while leaving every other option's position and sense untouched — `check` and `sign` are build policy, not tooling — and `RUSTC_WRAPPER`, `CCACHE_DIR` and `SCCACHE_DIR` join `_ENV_EXPORT_DENY`, closing the same hole on the Rust side, where a `RUSTC_WRAPPER=sccache` inherited from a profile would have broken every Rust package the moment the ccache error stopped masking it. Stripped rather than installed into the chroot because the accelerators cannot function there in any case: `makechrootpkg -c` resets the working copy each build and no cache directory is bind-mounted, so the hit rate is structurally zero and there is nothing traded away. A conf that sets no `BUILDENV` gets no line, since makepkg's own default already disables both. Sandbox path only; host builds keep the user's `BUILDENV` and wrapper exactly as configured.

- **`3.2.0-B3` — the progress indicator no longer vanishes for the length of a sandboxed build.** The bottom bar holds its row with a DECSTBM scroll region, and `pty_runner.run_with_pty` keeps a subprocess out of that row by sizing the child's pty one row shorter than the terminal. A window size belongs to the tty *device* rather than the file descriptor, though, and the child's stdin was left inherited from the real terminal — so `fd0` reported the full height while `fd1` reported the reserved one. That mismatch is invisible to a child that only writes, which is why the host build path was unaffected, but the sandbox inserts a pty-allocating layer: `makechrootpkg` re-execs under `sudo` and `arch-nspawn` runs `systemd-nspawn --console=autopipe`, which selects its interactive console *because* stdin is a tty and then seeds the new inner pty from it. The container therefore ran at the terminal's full height, scrolled straight over the reserved row, and nothing repainted the bar — a package build sits inside a single `tick()`, so the indicator stayed gone until the next package. Under a reservation the child's stdin is now the same pty as its stdout, so both descriptors agree and the nested pty inherits the reservation. Scoped to that case: with no rows reserved stdin is inherited exactly as before, keeping TTY-only prompts working, and the interactive build branch, which deliberately inherits the parent's stdio so prompts stay visible, is untouched. Sharing the pty also stops a non-interactive child from consuming the user's keystrokes.

- **`3.2.0-B4` — a clang profile no longer fails every sandboxed build for want of a compiler.** With `3.2.0-B2` clearing the accelerator error, sandboxed builds got far enough to reach their own `build()` and then died there, four of five packages in an `update` run: `CMake Error: Could not find the compiler specified in the environment variable CC: clang`, and `meson.build:4:0: ERROR: Compiler clang cannot compile programs`. The clean chroot is `base-devel`, which ships gcc and binutils and no LLVM at all — while `chroot_conf_text` appends the profile's resolved toolchain (`CC=clang`, `CXX=clang++`, `LD=ld.lld`, `AR=llvm-ar`) as `export` lines, because the conf is the only channel that survives `sudo -iu builduser`. This is the same category `3.2.0-B2` named — an env value pointing at a host binary the container does not carry — extended to the largest such values in the set, which that fix had not audited; it took the ccache error being cleared for them to become reachable. The remedy is the opposite one, though, because an accelerator is free to drop while the compiler *is* what the profile asked for: `missing_toolchain` probes the binary-valued keys against the chroot root and `provision_toolchain` installs what they map to via `arch-nspawn <root> pacman -S`, before `makechrootpkg` is spawned. Installing into the root copy rather than the working one makes it a single cost per chroot, since `-c` resets only the working copy. The probe resolves an **absolute** `CC` inside the chroot rather than against the host — the host has a binary sitting at that path, which is precisely why this shipped unnoticed on a workstation where clang is everywhere. A binary with no known package raises `SandboxUnavailable` naming the `arch-nspawn` command that installs it, since guessing a package name installs the wrong thing and continuing merely buys back the original cryptic failure — and either way the refusal now lands before the build rather than after a full source checkout and configure, per package. Falling back to the chroot's gcc was rejected: it produces a gcc-built package under a clang profile, which is the silent downgrade the sandbox's preflight rule exists to prevent. Sandbox path only.

- **`3.2.0-B5` — a sandboxed build no longer fails on a chroot whose package databases have gone stale.** With `3.2.0-B4` installing the profile's toolchain into the chroot, every package of an `update` run failed at that install instead — `error: failed retrieving file 'clang-21.1.6-1-x86_64.pkg.tar.zst' ... The requested URL returned error: 404`, repeated across every mirror in the list, then `failed to commit transaction`. Nothing re-syncs the chroot's *root* copy: `makechrootpkg -c` reseeds the working copy from it, and `arch-nspawn` hands the container the host's `pacman.conf` and mirrorlist while leaving its `/var/lib/pacman/sync` databases untouched. Those databases are therefore as old as the chroot — nine months, on the machine this was found on — so B4's `pacman -S` resolved a filename that had long since rotated off every mirror and 404'd on all of them. The two halves of the fetch come from different places, which is what made the failure read as a network or mirror problem rather than a stale-database one, and why the error text names a version the host has not carried since last year. The install is now `-Syu`. Not `-Sy`: refreshing the databases alone would install a current `clang` against months-old dependencies — a textbook partial upgrade, which breaks the chroot itself rather than merely the build, and would surface later and further from its cause. `-Syu` on the root copy also matches what devtools' own chroot maintenance does. The `SandboxUnavailable` message for an unmappable binary names `pacman -Syu <package>` for the same reason, since a user running it by hand hits the identical stale-database wall. One-time cost per chroot, on the same path B4 established; host builds are untouched.

- **`3.2.0-B6` — the sandbox now installs the linker the profile selects through its flags.** With `3.2.0-B5` getting the toolchain install to complete, sandboxed builds reached their own `build()` and died there instead, all six packages of an `update` run: `clang: error: invalid linker name in argument '-fuse-ld=lld'`, and from meson `ERROR: Unable to detect linker for compiler`. The chroot had clang and no lld, because `missing_toolchain` probes only the binary-valued conf keys (`CC`, `CXX`, `LD`, `AR`, ...) and this profile never sets `LD`: it picks its linker with `LDFLAGS=-fuse-ld=lld`, where the binary name appears inside a flag string. The package table already mapped `ld.lld` to `lld` — the knowledge was present and simply never consulted, since the probe was reading the wrong half of the conf. `-fuse-ld` is the one exception to "a flag value names no binary", so it is the only thing extracted: `_FUSE_LD_RE` is matched against `LDFLAGS`, `CFLAGS` and `CXXFLAGS` (it is a driver flag, legal in all three), and everything else in those strings stays invisible to the probe — scanning them generally would turn every `-march=native` into a package lookup. The flag names a linker *flavour* rather than a binary, so the value is resolved the way the driver resolves it, `lld` to `ld.lld`, with an explicit path taken as written; `mold` joins the package table alongside the `bfd`/`gold`/`lld` entries already there. This is the same class as `3.2.0-B4` and its predecessors, one layer further in: each fix let the build advance to the next host-only assumption baked into a conf that was written for the host. Sandbox path only, and it changes what is installed into the chroot, never what is built.

---

- **`3.2.0-B7` — the sandbox now finds the profile's linker where it actually lives.** `3.2.0-B6` taught `missing_toolchain` to read `-fuse-ld=` out of `LDFLAGS`/`CFLAGS`/`CXXFLAGS`, and the next `update` run failed all six packages at the identical point it had before: `clang: error: invalid linker name in argument '-fuse-ld=lld'`. The extraction was correct and was reading a dict that structurally cannot hold the answer. Flag variables never travel in `extra_env` — that carries `CC`, `CXX` and the profile's env-type keys only — they reach the container inside the makepkg conf body that `chroot_conf_text` copies wholesale, so probing `exports` for `LDFLAGS` finds nothing and the chroot is provisioned with clang and no linker behind it. The giveaway was in the log all along: not a single `[SANDBOX]` line, meaning the probe reported nothing missing and `pacman` was never run. `missing_toolchain` and `provision_toolchain` now take the emitted `conf_path` and read both channels, since a stage may still inject a flag through the environment; the conf values are unquoted first, because `parse_system_makepkg_conf` returns them verbatim and a bare `\S+` capture over `LDFLAGS="... -fuse-ld=lld"` yields `lld"`, which maps to no package. This is the fifth fix on one seam — B2, B4, B5 and B6 were each a host-only assumption riding into the container in that copied conf — and the first to close the gap between the two: the conf is what gets transported, and until now `exports` was the only thing audited. Sandbox path only, and it changes what is installed into the chroot, never what is built.

- **`3.2.0-B8` — makepkg's output no longer arrives with `(B` scattered through it.** Every message makepkg's helpers print closes with `ESC ( B` (designate ASCII into G0) beside the SGR reset, and `strip_ansi` matched none of it: its three branches cover OSC, CSI, and the two-byte C1 escapes (`\x1b[@-Z\\-_]`), while `(` is `0x28`, an *intermediate* byte from the nF class that no branch accepted. The sequence therefore survived whole, and because `ESC` does not print, what reached the terminal and the log was a bare `(B` glued to the text — `==>(B Retrieving sources...(B`, 148 times in a single `update` run. A fourth branch matches the class properly (`ESC`, one or more intermediates `0x20-0x2F`, a final byte), so the G1/G2/G3 designations and the line-drawing set go with it rather than leaving the same corruption one escape over. It is ordered after CSI and OSC, whose second bytes (`[`, `]`) fall outside the intermediate range and so cannot be captured by it. This also matters beyond cosmetics: `strip_ansi` exists so that substring matching runs against visible text, and a stray `(B` sits inside exactly the tokens the build classifier reads.

- **`3.2.0-B10` — a PGO profile no longer makes the sandbox look like it has no compiler.** With `3.2.0-B7` provisioning the linker, an `update` run went from six failures to one, and mesa failed with `meson.build:4:0: ERROR: Compiler clang cannot compile programs` — the `3.2.0-B4` symptom, on a chroot that now has clang. The cause was in the flags: the PGO stage injects `-fprofile-use=/var/cache/sysforge/pgo-mesa/mesa.profdata`, that store exists only on the host, and clang treats an unreadable profile as a hard **error** rather than a warning (`error: Error in reading profile ...: No such file or directory`), so meson's compiler sanity check fails and reports the compiler itself as broken. The two failures being textually identical is the whole reason this read as a repeat of B4 — the message names neither the flag nor the file. `host_profile_data` collects the input-file profile flags (`-fprofile-use`, `-fprofile-instr-use`, `-fprofile-sample-use`) from both the conf and the exports, and `provision_profile_data` copies each one into the chroot **at the same absolute path**, so the token already baked into CFLAGS/CXXFLAGS/LDFLAGS resolves unchanged inside the container and nothing has to rewrite flags on the way in. The `-fprofile-*generate` family is deliberately not carried: those name an output directory, so there is nothing to copy, and a container that writes profiles and is then discarded is a separate problem. Copying is unconditional rather than skipped when a mirror exists, because the store is rewritten by every `--pgo=use` merge and a stale mirror would silently pin the container to an old profile — a wrong-output bug in place of a loud one. Results are deduplicated, since `makepkg_conf` injects one token into all three flag variables; a path absent on the host is skipped, as there is nothing to copy and the host build would fail on it identically. A failed copy raises `SandboxUnavailable`: continuing hands clang a flag naming a file that is still missing, and dropping the flag would build a non-PGO package under a PGO profile, which is the silent downgrade the sandbox refuses on principle. Sixth fix on one seam, and the first where the host-only value is a data file rather than a binary.

- **`3.2.0-B13` — the progress bar now moves during a build instead of freezing on one line.** `3.2.0-B9`'s raw pty dump and `3.2.0-B11`'s region trace together settled what was actually wrong, and it was neither of the things suspected. The trace of a full run recorded exactly one `establish` at start and one `release` at shutdown, no resize and no mid-run teardown, while the dump showed the child emitting no `ESC[r`, no `RIS`, no alternate-screen switch and no absolute cursor positioning — so the region was never destroyed and nothing ever scrolled over the reserved row. What the trace did show was a **379-second gap between two consecutive paints**, against a 4-second runner-up: a whole package build sits inside a single `tick()`, so the bar painted `[1/1] building · mesa-sysforge` and was not touched again until the build ended six minutes later. A frozen bar under fast-scrolling build output is indistinguishable from a dead one. The machinery to fix it was already present and simply not connected: `pty_runner`'s idle callback fires every `MAKEPKG_HEARTBEAT_S` with the child's latest `\r`-redrawn status (ninja's `[X/Y] Building ...`), and `makepkg_invoke._on_idle` wrote it to the per-package log and nowhere else. It now also calls `progress.heartbeat(detail)`, which repaints the current count with live detail and advances nothing. Detail replaces rather than appends, since it fires for the whole build and appending would grow the line without bound, and the next `render()`/`phase()` overwrites it by setting a new base. No-op before any status exists and in plain mode, where painting goes through `log.ui()` and a 30-second repaint would append to the log forever. A second benefit falls out of the same change: the reserved row is now rewritten every heartbeat, so anything that corrupts it is repaired within the interval instead of persisting for the rest of the build.

- **`3.2.0-B14` — the persisted failure tail now contains the failure.** At normal verbosity the live build stream only reaches the terminal, so `invoke_makepkg` writes the last `MAKEPKG_FAILURE_TAIL_LINES` (80) of captured output to the per-package log specifically so a failure is diagnosable after the fact without a `-vvv` re-run. A blind `lines[-80:]` assumes the failure is the last thing said, which the build tools flatly contradict: ninja keeps running its other targets after one fails, and a PGO build emits a `-Wbackend-plugin` skew warning per function. On a real mesa failure the window held **61 skew warnings and zero error lines** — ninja's `FAILED:` block and rustc's `error[E0605]` had been pushed clean out of it, and the tail explained nothing at all. The error was only recoverable because `3.2.0-B9`'s dump happened to be running, which is not the normal case. `select_failure_tail` anchors the window on the **last real failure marker** (`FAILED:`, `error:`, `error[`, `fatal error:`) plus a few lines of lead-in, rather than on the end of the stream. makepkg's own `==> ERROR:` epilogue is explicitly excluded from anchoring — it matches the marker vocabulary and is the last line on every failure, so honouring it would re-anchor on the end and reproduce the exact bug — but remains a fallback anchor when nothing else was captured. When the anchor already sits inside the ordinary last-80 window, which is the common case, the result is the old contiguous slice unchanged. When it does not, the closing lines are appended as well, since `==> ERROR: A failure occurred in build()` names the failing phase, and the two segments are joined by an explicit `... N line(s) omitted ...` marker so they are never mistaken for contiguous output. Replayed against the mesa capture the same 80-line budget now carries the `E0605` diagnostic and its source context where it previously carried none.

## Security

- **`3.0.0-B3` — a killed bootstrap no longer leaves the target with passwordless root.** The configure stage writes `/etc/sudoers.d/99-sysforge-bootstrap-build` granting the build user `NOPASSWD: ALL`, because `makepkg -s` must sync makedeps non-interactively while building sysforge inside the target. The `finally` that removes it covers exceptions and non-zero exits, but not `SIGKILL`, an OOM kill, or power loss mid-build — any of which left a freshly installed system carrying an unconditional passwordless-root rule for its primary user, in a file the user has no reason to look for. Low likelihood, maximum blast radius, and silent: the install looked incomplete rather than insecure. Two independent fixes, taken together. The rule is now scoped to `NOPASSWD: /usr/bin/pacman` — the one binary makepkg actually needs — so even a leaked drop is not root-equivalent; and stale `99-sysforge-bootstrap-*` drops are swept at bootstrap entry, so a `--resume` after a kill cleans up its predecessor. The sweep runs on the path that would otherwise re-create the file, since a `pre_check` refusal would block the very run capable of cleaning up.
