## Added

- **`3.1.0-F2` — `sysforge state failed --names` feeds last run's failures back into a retry.** `state failed` already knows exactly the set a user wants to retry after a partial `update`, and `build` takes several package names, but the two could not be composed: the verb rendered only a padded, paged table, and there is no machine-readable output mode anywhere in the CLI. The workarounds were scraping the table (coupled to column padding) or reading `build_state.toml` directly (a schema documented as internal). `--names` prints only the failed pkgbases, one per line, with no header and no pager, and nothing at all when nothing failed. `sysforge build $(sysforge state failed --names) --makepkg=-f --interactive` is now the supported retry. The mode is verb-local on purpose, since this is the one listing whose output is already a set of package names; a CLI-wide machine-output mode would be a separate decision. It has its own name because the global `--quiet` already means verbosity 0.

---

- **`3.2.0-F11` — `sysforge state profiles` lists and reclaims the shared profile store.** The PGO, AutoFDO, Propeller and BOLT profiles under `/var/cache/sysforge` were write-only from the user's side: nothing listed what was there, how old it was or which package it belonged to, and nothing reclaimed it. The purge path `makepkg_pgo`'s docstring promised was never written. `sysforge state profiles` lists every non-empty store with size, age and, where recorded (`3.2.0-B16`), the version a profile was collected against. `--purge <method>[/<target>]` deletes one store after a confirmation; it refuses an unknown method and refuses to run without a terminal, because a profile needs a workload to regenerate. Removing a package still never deletes its profile (the profile's presence is what keeps later rebuilds profiled), but `revert-to-stock` and `uninstall` now name any store they leave behind and the command that reclaims it. The stale docstring is corrected.

---

- **`3.2.0-F15` — a post-build lint names config a package places where its consumer never reads it.** `cosmic-greeter-git` once installed its PAM file under the *directory* `/etc/pam.d/cosmic-greeter/`, where PAM resolves a service to the flat file `/etc/pam.d/<service>`. PAM fell through to `pam.d/other`, `XDG_RUNTIME_DIR` was never created, and `cosmic-comp` panicked on every greeter restart, an unbootable desktop from a one-flag packaging slip. Authentication still succeeded, and nothing in the build, `pacman -Qkk` or the install logged anything. After every build, `primitives/payload_layout.py` now lists each package's members once and warns (non-fatally) on any file nested deeper than a non-recursive consumer looks: `/etc/pam.d`, `/etc/sudoers.d`, `/usr/lib/sysusers.d`, `/usr/lib/tmpfiles.d` and `/etc/ld.so.conf.d`. It deliberately takes no general `/etc` stance, so config trees that legitimately nest stay silent. Each finding is also repeated in the end-of-run summary of `update` and `build`, including single-package builds, so it is visible at default verbosity. New standards row 28 cites each directory's spec and is held to the lint's table by its tests.

---

- **`3.2.0-F17` — `base_config_merge = "overlay"` keeps your kernel config and adopts the packager's choices for what is new.** A non-default `base_config` was copied over the PKGBUILD's `.config` wholesale, so across a version bump every symbol the base did not mention (anything new in this release) resolved to the upstream Kconfig default instead of the PKGBUILD's value. The new `kernel.toml base_config_merge` key (CLI `--base-config-merge`) defaults to `"replace"`, so `base_config = "running"` still means *exactly my config*. `"overlay"` merges the base onto the PKGBUILD's config with `merge_config.sh -m`: the base wins every symbol it names, `# CONFIG_X is not set` included, and the PKGBUILD fills the rest before `olddefconfig`. One edge: a symbol missing from the base only because its dependencies were off takes the PKGBUILD's value once they are on. A PKGBUILD that runs its own `merge_config.sh` skips the seed entirely, and the `base cfg:` summary line now says the base is inert there. Adopt the commented default into a live config with `make sync-config`.

---

- **`3.3.0-F2` — the progress bar keeps its clock moving, steps aside cleanly for prompts, and stops counting while you answer them.** The bottom bar used to repaint only when something happened: a tick, a phase change, or makepkg's 30-second idle heartbeat. So its elapsed time jumped every 30 seconds during a build and froze completely between items elsewhere, such as a long git fetch inside a source sync. It now refreshes about once a second, and only writes when the text has changed. Time spent at a prompt no longer counts as work. The build-failure recovery menu, review prompts and confirmations all pause the open batch's clock, so a minute spent deciding how to retry mesa neither shows up as build time nor inflates the ETA for the rest of the batch. During a build, the refresh waits until makepkg's forwarded output is between escape sequences and multi-byte characters, so it never splits cargo's or ninja's live redraws. Each repaint is a single write, so a log line from another thread can no longer interleave with it. Resizing the terminal no longer repaints from inside the signal handler. The terminal is released once on every exit path, Ctrl-C and fatal errors included, before the final message prints. Internally, `ui/progress.py` is rebuilt around one state object, one painter and one terminal-handover call (`yield_terminal`, which replaces `suspend_for_prompt`/`suspended` in the `progress_hooks` protocol). Opening one progress batch inside another is now refused instead of silently mangling the outer one. Plain (non-TTY) output is unchanged.

---

- **`3.3.0-F5` — sysforge-managed systemd-boot entries.** On systemd-boot the kernel stage only ran `bootctl update`, which refreshes the loader binary and never creates an entry, so every coexist kernel name needed a hand-written entry and Gate 3 failed the run after the build until one existed. The stage now writes `/boot/loader/entries/sysforge-<kernel>.conf` for each kernel it installs, cloned from the entry you booted (`options`, microcode and the rest), and re-renders every managed entry on each build so an edit to your own entry reaches them. Your own entries are never modified, renamed or deleted: a write onto an entry you own, even one named `sysforge-*.conf` without sysforge's header, is skipped with a note, and an entry of yours that already boots a kernel means nothing is written for it. Menu order follows the system's own keys: a `sort-key` template is copied, otherwise the filename decides, and the new `boot_entries_prefix` key (for example `"97"`) opts into numbered filenames. A new `boot_entries = "manage" | "off"` key (default `"manage"`) turns it off for UKI or `kernel-install` setups. Preflight refuses early when the boot path is not `/boot` or no entry can be cloned, and a failed write after install says the kernel is installed and how to recover. `sysforge update` and the stage prune entries whose kernel is gone, `doctor` reports `boot_entry_dangling` and `boot_entry_template_gone`, and `sysforge state boot-entries` lists each kernel with its entry, owner and template. For an AutoFDO profiling (`--autofdo=record`) build, the `-v` advisory includes the exact `sudo bootctl set-oneshot <file>` command; for any other kernel, run `sudo bootctl set-oneshot <entry-id>` yourself. Sysforge refuses to write an entry whose `linux` or `initrd` paths would not exist under `/boot` (for example a subdirectory template layout), says which are missing and points at `boot_entries = "off"`; a fallback-initramfs template is rewritten to the new kernel's main initramfs, and `update --dry-run` never prunes entries. Adopt the commented defaults into a live config with `make sync-config`.

---

- **`3.3.0-F6` — kernel FDO builds get their own names, and `kernel.toml [fdo] mode` keeps one applied.** An `--autofdo=use` build installed as `<pkgname>-sysforge`, and with the shipped `pkgname = "linux-sysforge"` that is the plain kernel's own name, so the optimized kernel silently replaced the plain one instead of installing beside it. The guide's only defence was a note to rename the kernel first. The optimization also lasted one build: the next plain `sysforge run kernel`, such as the rebuild after a kernel update, went back to an unprofiled kernel unless the flags were repeated. Each role now has its own name: `pkgname`, then `-sysforge` if absent, then one role suffix. The profiling kernel of either round is `-profiling` (`linux-sysforge-profiling`), the AutoFDO build `-fdo` and the AutoFDO + Propeller build `-propeller`, while `linux-sysforge` stays the plain kernel. Each installs beside the others (with its own boot entry where sysforge manages them), and `sysforge search` lists each as an installed variant of the stock kernel. The new `kernel.toml` `[fdo] mode` (`"off"` by default, `"autofdo"` or `"propeller"`) makes a plain `run kernel` a `use` build. An explicit `--autofdo=…` still wins, and `record`/`capture` are never implied. A config-driven build bends rather than breaks on a kernel update. `"autofdo"` with a profile collected on another major.minor builds and warns. `"propeller"` whose round 2 sampled a different `pkgver` (or a kernel whose PKGBUILD computes its version during the build) builds AutoFDO only as `-fdo` and warns that the older `-propeller` kernel stays installed; sysforge never removes it. With no profile at all, the build refuses before it starts, and the message names `kernel.toml`, not a flag. While `mode` is set every plain run builds the optimized kernel, so the plain kernel is not rebuilt; set `mode = "off"` for a run to rebuild it. The boot-safety preflight now checks the role-named kernel being replaced, so the plain kernel counts as its fallback. Migrating: with the shipped `pkgname`, the old use-built `linux-sysforge` now simply reads as the plain kernel and the next `use` installs `linux-sysforge-fdo` beside it; with another `pkgname` the old `<pkgname>-sysforge` use-build (for example `linux-mine-sysforge`) is no longer built, so remove it by hand once the new `-fdo` kernel boots. The old profiling kernel was `<pkgname>-sysforge-fdo` taken literally (`linux-sysforge-sysforge-fdo` by default) and can be removed with `sudo pacman -R`. Only a `pkgname` without `-sysforge` collides with the new AutoFDO name (`linux-mine-sysforge-fdo`), so check which one you have with `pacman -Qi` (build date) before removing it. Adopt the commented `[fdo]` block into a live config with `make sync-config`, or add `[fdo]` by hand above `[[kconfig]]` on a packaged install.

## Changed

- **`3.2.0-STD1` — the release preflight now runs lint and typecheck.** `typecheck` ran only in `make pre-release`, which is advisory; `tools/release.sh` preflight, the gate a release cannot skip, never called it. `v3.2.0` shipped four pyright errors, one of them the live BOLT crash (`3.2.0-B30`) the type-checker had named weeks earlier, and the 3.3.0 cycle reached eighteen. The preflight now runs `make lint` and `make typecheck` beside the five shared `check-*` gates and fails the release on either. The full test suite stays in the heavier tier by design. New standards row 27 (release-gate completeness) is enforced by a `check_standards` `release_gates` group that diffs `pre-release`'s prerequisites against the targets the script invokes, so `docs/RELEASE-CHECKLIST.md`'s gate table cannot silently diverge again. Because these gates now block a release, the tools they fetch per run are pinned (`PYRIGHT_VERSION = 1.1.414`, `REUSE_VERSION = 6.2.0` in the Makefile), and the same group fails on an unpinned `uv run --with` in any gate recipe. Bump a pin deliberately in its own commit.

- **`3.3.0-DOC1` — a step-by-step guide to profile-guided optimization.** PGO in sysforge spans three surfaces (`build --pgo=record|use`, the toolchain stage's PGO bootstrap, and `run kernel --autofdo`/`--propeller`), and the only documentation was DESIGN.md, which explains how each is wired rather than how to use it. Nothing told a newcomer that the record step is only as good as the workload run between `record` and `use`, that Mesa PGO does nothing for games on the proprietary NVIDIA driver, or that profile data silently fails to reach a store the writing process cannot see. `docs/guides/pgo.md`, linked from the README, walks through choosing a method, the prerequisites (LLVM toolchain, `sysforge` group membership for the store, `cache = false`), each workflow end to end, workload practice for gaming (cold shader caches, API coverage, balanced sessions, the Steam Runtime container's store access), keeping and refreshing a profile, `state profiles`, and troubleshooting.

---

- **`3.3.0-DOC2` — a guide to sysforge-managed boot entries.** `docs/guides/boot-entries.md`, linked from the README, explains what sysforge writes and never touches, how systemd-boot orders the menu (and the "higher number lists higher" consequence), how to predict a filename's position with `systemd-analyze compare-versions` and check the real menu with `bootctl list`, ordering by numbered filenames with `boot_entries_prefix`, systems that use `sort-key`, why the default entry is a separate setting, booting a kernel once with `bootctl set-oneshot`, and turning managed entries off.

- **`3.3.0-DOC3` — the kernel AutoFDO / Propeller guide walks both rounds.** The kernel section of `docs/guides/pgo.md` was three commands and a few bullets. It said nothing about which kernel had to be running at each step or when to reboot, it still named a converter sysforge no longer prints, and it described Propeller as one flag added to the same three steps. The section now covers the prerequisites (`perf`, `llvm-profgen`, `generate_propeller_profiles` for round 2, keeping the build tree until the conversion), the per-role kernel names, and round 1 and round 2 each with a table of the booted kernel and the reboot for every step. It explains how to capture a good profile: start the workload first, match your real mix, and know that re-running replaces rather than merges. A `llvm-profdata show --sample --topn=20` check shows whether the capture saw real work. It also covers keeping the profile applied with `[fdo] mode` and what happens on kernel updates, removing the profiling kernel afterwards, upgrading from the old names, and a troubleshooting row for each new refusal and warning. The "Check your kernel name" advice is gone, since `3.3.0-F6` makes it moot.

- **`3.3.0-STD1` — documentation changes get their own `DOC` roadmap ID type.** User-facing doc work had no fitting type: a guide is neither a bug nor a feature, and filing one as `F` under `## Added` would make the derived SemVer bump demand a minor release for a change no API consumer sees. `DOC` IDs (`make next-id TYPE=DOC`) cover guides under `docs/guides/`, the README and the man page, and sort between `B` and `F`. The `changelog` check now refuses a `DOC`-filed entry anywhere but `## Changed`, so documentation can only ever imply a patch bump; a `DOC` cited as a cross-reference in another entry is unaffected. Internal docs (`docs/design/`, `CLAUDE.md`, `ROADMAP.md`) stay unnumbered, and wrong `--help` or man output remains a `B`, since it is CLI behaviour. Standards row 13 is extended accordingly.

---

- **`3.3.0-STD2` — contributor-only work gets its own `DEV` roadmap ID type.** A fix to the test suite or the dev tooling had to be filed as a `B` and listed under `## Fixed`, where it read as a user-visible bug and made the derived SemVer bump call for a patch release that changed nothing a user runs. `DEV` covers work that touches only `tests/`, `tools/`, the `Makefile`, `.claude/` or dev-only docs; anything under `sysforge/` or a shipped file stays `B`/`F`. A `DEV` item files no release-note entry, and `make check-standards` rejects one. Its squash-commit subject carries the ID, and `make next-id` and the gap check now read commit subjects, so a shipped `DEV` number is never reissued. The collision check does not, because a subject that only files an ID is not a shipment.

## Fixed

- **`3.2.0-B12` — a `--pgo=record` build under the sandbox is now refused instead of silently losing its profiles.** `mesa_pgo.generate_flag` bakes `-fprofile-generate=<store>` into the flags. Under `[security] sandbox_builds` the instrumented package wrote its `.profraw` to that path inside the container, which `makechrootpkg -c` discards at teardown. The build succeeded, the profiles were gone, and the next `--pgo=use` found an empty store or reused a stale merge, with no diagnostic. The existing probes ask whether an *input* is present, which a generate flag (having none) always passes. `build_sandbox.refuse_profile_generate` now scans the conf and exports for the `-f[cs-]profile[-instr]-generate` family and raises `SandboxUnavailable` before any provisioning. The error explains that `--pgo=record` must run unsandboxed, after which `--pgo=use` may run sandboxed. Carrying profiles out at teardown or bind-mounting the store were considered and not taken: the first needs a hook that survives a failed build, and the second opens a host write channel inside the isolation boundary.

---

- **`3.2.0-B16` — a reused mesa PGO profile now says how old it is.** The `llvm-pgo` store records the LLVM major its profile was collected against (`clang.profdata.version`), but `pgo-mesa` wrote no sidecar, and its reuse check was a bare existence test. Every `sysforge update` rebuild therefore re-applied whatever profile was on disk with no bound on its age; on the development workstation, one profile collected against mesa `26.1.3` fed four later minor versions without a word. `mesa_pgo.merge_profraw` now writes `<pkgbase>.profdata.version` with the installed version of the instrumented build that produced the `.profraw`. On reuse, the `PGO (reuse)` line appends "profile collected against X, building Y; refresh with `sysforge build <pkg> --pgo=record`" when the versions differ, or "profile age unknown" for a profile collected before the sidecar existed. Unlike the LLVM gate, no verdict refuses the profile: mesa skew is gradual source drift, and discarding a profile that cost a workload to collect would be the worse regression.

---

- **`3.2.0-B21` — installing a libLLVM consumer outside the toolchain stage is now re-verified against the installed libLLVM.** Only the toolchain stage (after libLLVM changes under its consumers) and `doctor` asked `toolchain_safety.check_installed_consumer_symbols`. The reverse direction, a *consumer* changing on top of an unchanged libLLVM, had no post-install check, which is how the 2026-09-11 `mesa-sysforge` 26.2.2 install reached a reboot before anything named the cause. `3.2.0-B20` already refuses the known shape from the package archive before `pacman -U`. `build_core.build_and_install` now also runs the same symbol fact after its final install whenever an installed package is libLLVM or depends on it, and reports each finding as an error naming the consumer and how to roll back (pre-build snapshot or `pacman -U` of the previous package). It is the backstop for what an archive scan cannot see: a split member pulling another soname, or a dependency JIT-installed mid-batch.

---

- **`3.2.0-B22` — the `mesa_llvm_symbols` finding tells apart the two ways a consumer loses its libLLVM symbols.** `toolchain_safety.check_installed_consumer_symbols` explained every std:: drift finding as "the PGO libLLVM inlined away the weak std:: copies, so rebuild the consumer". That fits a libLLVM rebuilt under an existing consumer. On 2026-09-13, though, `doctor` said the same about a mesa that had been *built* against the repo libLLVM inside a sandbox container, where rebuilding the same way reproduced the identical broken package. Against the installed libLLVM, the finding now compares the consumer package's build date with the libLLVM package's install date (new `pacman.get_package_dates`). A consumer built after that install was linked against a different libLLVM build: the finding says so, points at how it was built (a sandboxed build must inject the host's libLLVM), and tells the user to restore the stock package meanwhile, without offering the rebuild. Otherwise, or when a date is unknown, the wording is unchanged.

- **`3.2.0-B24` — toolchain tests no longer take the host's real PGO build lock.** `pgo.pgo_lock_path` puts the lock beside `staging1`, which defaults to `/var/tmp`, and fifteen toolchain tests (four in `test_stage_toolchain.py`, eleven more through the shared `_pgo_setup` helper) overrode `pgo_staging` but not `pgo_staging1`. They locked `/var/tmp/sysforge-pgo.lock`, so they failed whenever a real `sysforge run toolchain` was running and could block one from starting. Every PGO test config now scopes `pgo_staging1`/`pgo_staging3` into `tmp_path`, and the shared autouse `_toolchain_gates_clean` fixture wraps `pgo.pgo_lock` to fail any test whose lock path falls outside `tmp_path`, so a future leak fails deterministically instead of only under load. Test isolation only; no user-visible change.

---

- **`3.2.0-B37` — Gate 2 and the kconfig drift check now read the kernel build tree the build actually used.** Both searched the *system* `makepkg.conf` `BUILDDIR` under the *checkout* name, while a profiled kernel build runs with the profile's `BUILDDIR` (`$HOME/builds`) and makepkg names the tree after the post-rename pkgbase (`linux-sysforge`). Every renamed kernel build therefore logged `Gate 2: resolved kernel .config not found in build tree` and installed with the boot-critical audit silently off. `makepkg_wrapper.run` now returns the tree it built in (`makepkg_env.build_root`: profile `BUILDDIR`, falling back to the system conf, keyed on the authoritative pkgbase), and the kernel stage passes it to Gate 2, the drift check, the kconfig history and Gate 3. A fresh build whose reported tree has no `.config` now aborts before install (override: `--skip-boot-audit`); only the AlreadyBuilt path, which has no fresh tree, keeps the warning.

---

- **`3.2.0-B38` — kernel builds are recorded in `build_state.toml` again.** Since 2.6.1-F23 added the kconfig VERIFY check to the kernel's `prepare()`, no kernel build had been recorded: the entry stayed at the last build before it (7.1.6, 2026-08-08) while newer kernels were installed, so `update` judged the kernel against August's flags. The run log still said `Recorded build state for 'linux-sysforge'`, which read as a record lost after it was written. The record was never written. The static PKGBUILD parser treated every unquoted `#` as a comment, so the check's `${_line#*=}` was cut to `${_line` and `prepare()` never closed. Every global declared after it vanished, the stock kernel's `pkgname` included, and the rename handed the recorder an empty package list. The parser now follows bash's rule: `#` starts a comment only when it begins a word. The same fix corrects other PKGBUILDs it had been misreading: `source=` URLs lost their `#tag=`/`#commit=` pins (one array swallowed the `b2sums=` line after it), and derived names like `${pkgname#python-}` were truncated. A build that resolves no package names now warns that nothing was recorded instead of claiming it was.

---

- **`3.2.0-B39` — a profile flag change no longer reports the kernel as drifted.** Kernel builds strip `CFLAGS`/`CXXFLAGS`/`CPPFLAGS`/`LDFLAGS` and the `DEBUG_*` variants from the emitted conf (`profile.KERNEL_CLEAN_KEYS`; the kernel takes its optimisation from Kconfig), but flag drift still diffed the full serialized profile. Changing the `optimized` profile (`-O2` → `-O3 -fno-plt`, `--icf=all` in `LDFLAGS`) therefore flagged `linux-sysforge`, the most expensive rebuild in the system, although nothing about its build would change. `serialize_effective_flags(kernel_build=True)` now drops those keys on both the record and the replay side, and `flag_drift` strips them from an existing kernel record before diffing, so records written before this fix converge without one last false drift. Only keys that reach the kernel build (`CC`, `LD`, `RUSTC_WRAPPER`, …) can drift; non-kernel packages are unchanged.

---

- **`3.2.0-B40` — the flag-drift notice now says what it will actually rebuild.** With `--rebuild-on-flag-drift` on, the Phase 4.3 `ui()` line picked its hint from the flag alone (`… rebuilding (--rebuild-on-flag-drift)`), but only drifted packages in the run's package walk get promoted. Stage-owned packages (the kernel, the toolchain) are found by the build-state-wide fold and never queued, and the `warn()` saying so was hidden at default verbosity, so a default `update` announced it was rebuilding `linux-sysforge` and then did nothing. The line is now built from the same predicate the promotion uses (`update._partition_flag_drift`). It lists what is being rebuilt and, separately, what drifted but was not queued, each with the command that would rebuild it: `sysforge run <stage>` for a stage-owned package, `sysforge build <pkg>` otherwise. The now-redundant hidden warning is gone.

---

- **`3.3.0-B1` — switching `base_config` back to `"pkgbuild"` no longer keeps applying an old base config.** The kernel's base-config seed step runs whenever a `sysforge.base.config` file exists next to the PKGBUILD, and `write_base_config` returned early for `"pkgbuild"` (and for `"running"` when no running config could be read) without removing a seed an earlier run had written. The file lives in the untracked source checkout and is never cleaned, so after switching back to `"pkgbuild"` every build silently kept seeding the old running-kernel config, and the "falling back to the PKGBUILD base" warning was false. A run with no base text now removes both seed files (`sysforge.base.config` and `sysforge.base.overlay.config`), the same rule the hotplug fragment already follows. `--dry-run` still changes nothing.

---

- **`3.3.0-B2` — a build installed on a rerun now keeps its build record.** When a fresh build's install is refused (a sudo prompt that timed out on an unattended run, a file conflict, the ABI-skew gate), `build_state` correctly goes back to the version still installed. But the rerun finds the artifact already built, skips `makepkg_wrapper`, and installs it without recording anything, so the record kept describing the old build: its flags, toolchain and upstream commit. Flag drift then compared against the wrong build, and `--devel`'s ls-remote shortcut missed and took the slow path every run. Seen on `wayland-git`: r14 built and recorded, refused twice for sudo timeouts, then installed on the third pass while the record stayed at r13. The revert now keeps the entry it undid, keyed by artifact filename, and puts it back once pacman installs that exact file. That covers the just-in-time and final installs and `update --install-only`. A newer build of the package drops the stash, so installing a stale artifact never rolls the record back.

---

- **`3.3.0-B3` — quitting the pager early, or piping into `head`, no longer prints a `BrokenPipeError` traceback.** `maybe_pager` points `sys.stdout` at the pager's stdin. If you press `q` before a verb has finished writing, less exits and the verb's next `print()` raises `BrokenPipeError`. Only `sysforge log` caught it, so `state list` (whose untracked-foreign section prints after a slow pacman query), `state failed`, `state orphans`, `state profiles` and `config merge`'s `[v]iew` could all crash with a traceback. The seam now absorbs the error: the rest of the paged output is skipped and the verb exits normally. Without a pager, piping any verb into a reader that quits early (`sysforge state list | head`) crashed the same way, and even `sysforge log`'s own guard only moved the failure to an exit-time flush error. `sysforge` now exits quietly with 141 (128 + SIGPIPE), the status the shell reports for any tool cut off by a closed pipe.

---

- **`3.3.0-B4` — a compiler/linker swap from the build-failure menu now applies the linker you picked.** When a PKGBUILD sets its linker inside `build()` (for example `RUSTFLAGS+=" -C link-arg=-fuse-ld=mold"`), sysforge rewrites that token to the profile's linker before the first attempt. A `[c]` retry only re-emitted makepkg.conf, and cargo never reads LDFLAGS, so the rewritten `-fuse-ld=lld` stayed in force whatever `LD` you chose. The retry now rewrites the token in the patched PKGBUILD to the swapped linker. If the swap also fails, the token goes back to what it was, so a later retry-as-is runs as it did originally. Leaving `LD` blank now keeps the linker the failed build used, including one set with `--ld`; previously it fell back to the profile's. After a failed swap, the `Toolchain used` line showed the original `CC`/`CXX`/`LD`, which made the swap look ignored. It now shows the toolchain the retry ran with. Seen on `cosmic-viewer-git`, a gcc + mold swap that still linked with lld.

- **`3.3.0-B5` — the PGO toolchain build no longer fails on a major LLVM upgrade.** The staged passes build `clang` against a freshly built libLLVM in `/var/tmp/sysforge-llvm-stage*`, and on purpose never set `LD_LIBRARY_PATH`, so the host compiler cannot load that libLLVM by accident. But clang's build also runs helper programs it has just linked against the staged libLLVM, and Arch's `CMAKE_SKIP_RPATH=ON` removed the build-tree RPATH that would have pointed them at the stage. The loader then searched only `/usr/lib`. That went unnoticed while the staged and installed libLLVM shared a soname, but the first major upgrade broke Pass 2 with exit 127 (`libLLVM.so.23.1: cannot open shared object file`). Seen on 22.1.8 → 23.1.1. Staged passes now narrow the PKGBUILD's `CMAKE_SKIP_RPATH=ON` to `CMAKE_SKIP_INSTALL_RPATH=ON`. Build-tree tools keep the RPATH LLVM's CMake already gives them for the staged prefix, and installed binaries are still stripped to no RPATH, so packages are unchanged. Unstaged builds are not affected.

- **`3.3.0-B6` — `revert-to-stock` now reverts a PGO-optimized mesa (or any conflict-mode split build) instead of aborting.** Reverting an optimized build relies on one `pacman -S <stock>`, in which pacman removes the conflicting `-sysforge` build and installs stock in a single transaction. But sysforge passed `--noconfirm`, which answers pacman's `Remove mesa-sysforge? [y/N]` with its default N, so every such revert failed with `unresolvable package conflicts detected` and left nothing changed. The revert now adds `--ask=4` to confirm that one question. The `-U` install path has answered it the same way since it hit the same prompt, and the flag is passed only when the plan has established that the conflicting packages are sysforge's own renamed builds. Fixing the prompt exposed a second defect. Every member of a split build records the same `origin_pkgbase`, so `revert-to-stock mesa` resolved to whichever sibling sorted first (`mesa-docs-sysforge`) and would have reverted only that one entry. On a typical install that leaves sixteen `-sysforge` members (the Vulkan drivers, `opencl-mesa`, the layers) installed next to stock mesa: a version behind, no longer tracked, and never updated again. The revert now swaps every installed member of the set in the same transaction, each to its own stock name, then forgets all of them. Members that were built but never installed are left out, because there is nothing to swap.

- **`3.3.0-B7` — the test suite no longer reads or deletes the live PGO profile store.** `makepkg_wrapper.run()` ends by checking the toolchain PGO store for `.profraw`. Files newer than the build abort it as a sign that an instrumented LLVM has leaked onto the system, and older files are deleted as orphans. The test fixtures isolated the state dir, the pacman database and the soname cache, but not this store, so every test that reached `run()` (even with the build itself patched out) checked the real `/var/cache/sysforge/llvm-pgo`. While a `sysforge run toolchain` Pass 3 was writing training data, four tests failed intermittently on the false abort. When a test happened to see no fresh file, it deleted the run's not-yet-merged training data instead. A new autouse fixture points `SYSFORGE_PGO_STORE` and `SYSFORGE_PROFILE_STORE` at a throwaway tree for every test, and a guard test fails if the isolation is ever removed.

- **`3.3.0-B8` — a build started alongside `sysforge run toolchain` no longer aborts on, or deletes, the toolchain's PGO training data.** After every build, `run()` checks the toolchain PGO store for `.profraw`: files newer than the build mean an instrumented LLVM is still installed (a fatal error), and older files are leftovers to purge. While a toolchain PGO run is in Pass 3, though, that store is full of the run's live training data. So a `sysforge build` started at the same time either failed with a false "instrumented LLVM binaries may be installed" error, or, if no file happened to be newer than the build, deleted every `.profraw` the run's merge monitor had not read yet. Nothing reported it, and the profile simply came out thinner. The toolchain stage already holds `sysforge-pgo.lock` for its whole run. The check now probes that lock first with a new read-only `build_lock.is_held`, which never creates the file or overwrites the holder's PID, and while the lock is held it logs that it is deferring and leaves the store alone. The lock path moved to `primitives/makepkg_pgo.py` (`pgo_lock_path`, `resolve_pgo_lock_path`, `DEFAULT_PGO_STAGING_1`), so the check and the stage resolve the same file; the stage's `pgo_lock_path` and `DEFAULT_STAGING_1` now delegate to it. The check previously had no tests. Its fatal and purge behaviour is now pinned alongside the new deferral.

- **`3.3.0-B9` — `run toolchain --dry-run`, and the test suite, no longer delete a running build's staged LLVM.** Pass 4 clears `/var/tmp/sysforge-llvm-stage3` before unpacking the optimized libLLVM into it, and did so even on a dry run, which never takes the PGO build lock. A dry run started while a real `run toolchain` was in Pass 4b removed the headers clang was compiling against; clang 23 then fell back to the LLVM 22 headers in `/usr/include` and failed with errors such as `no member named 'getEmptyKey' in 'llvm::DenseMapInfo<unsigned int>'`. The test suite triggered it: two PGO dry-run stage tests used the live staging paths, so a `make test` started mid-build deleted that build's stage3. A dry run now only reports which staging prefix it would remove, and the tests' default staging paths point at a throwaway directory, as the PGO store and state dir already do.

- **`3.3.0-B10` — Gate 3 matches boot entries exactly.** `_boot_entry_references` accepted a bare substring of the package name, so an entry for `linux-sysforge-fdo` satisfied Gate 3 for `linux-sysforge` and a missing entry went unnoticed. On systemd-boot each entry's `linux` basename must now equal `vmlinuz-<name>`, and a `grub.cfg` line must match `vmlinuz-<name>` followed by whitespace or end of line. With managed entries on, coexist kernels no longer fail Gate 3 for lack of a hand-written entry.

- **`3.3.0-B13` — `--autofdo=capture` prints commands that work as printed.** The printed capture block failed for most setups. It looked for the profiling kernel's `vmlinux` only in the system `makepkg.conf` `BUILDDIR`, which misses the tree whenever a build profile sets its own `BUILDDIR`, and it fell back to a `<path-to-vmlinux>` placeholder. Nothing checked that the `vmlinux` matched the booted kernel. `perf record` under `sudo` wrote a `perf.data` only root could read, so the unprivileged converter that followed failed. The converter it named was a separate tool not tied to the clang that consumes the profile. `capture` now picks the `vmlinux` whose `Linux version` banner equals `/proc/version` exactly, searching the tree the `record` build actually used (kept in the store's `round.toml`), then the system `BUILDDIR` under the profiling name, then `/usr/lib/modules/<running>/build`. The banner carries the build host, compiler and timestamp, so a re-recorded kernel you have not rebooted into does not match. When it cannot print a working command it refuses with a non-zero exit and prints nothing runnable: when `perf` or the round's converter is not on `PATH` (with an install hint), when the running kernel is not the profiling kernel, when the build tree is gone, when the only matching `vmlinux` is a copy stripped of debug info (the `-headers` package's, which the converters cannot read), or when `/proc/version` cannot be read. The printed block now says to start the workload first, samples the whole system for 5 minutes (`-- sleep 300`; Ctrl-C ends early and keeps the data), `chown`s `perf.data` back to your user, and converts with `llvm-profgen`, which ships with `llvm` and matches the clang that consumes the profile. Every path is shell-quoted.

- **`3.3.0-B14` — Propeller profiles match the kernel they are applied to.** `--propeller` sampled the AutoFDO and Propeller profiles from the same un-optimized kernel, and the `use` build then applied both. Applying the AutoFDO profile changes code generation, so the Propeller profile described basic blocks the optimized kernel no longer had. The kernel's own Propeller documentation requires two rounds for this reason. `--propeller` now means round 2, after a completed AutoFDO round 1. `record --propeller` refuses without round 1's `kernel.afdo`, copies it into the Propeller store as a pinned copy, and builds the profiling kernel with that copy applied, so the kernel round 2 samples and the final `use --propeller` build share one AutoFDO profile even if round 1 is later redone. Each round's `record` writes a `round.toml` into its store with the profiled `pkgver`, the build tree `capture` searches, and in round 2 the pinned profile's hash. `sysforge state profiles` shows that `pkgver` as the collected version. `--autofdo=use --propeller` refuses when there is no round 2 record (a single-round Propeller store from before this change), when the pinned profile has changed since round 2, when the profile pair is incomplete, or when the kernel `pkgver` differs from the one round 2 sampled. When the building version is only known once makepkg runs, it warns that it cannot verify the match and proceeds. Both rounds build the same `-profiling` package at the same version, so round 2 used to find round 1's package already built and install it, without the pinned profile, the Propeller config or a build tree for `capture`. Every `record` now builds fresh. A `use` build also reinstalled the old package after a new capture at the same kernel version. sysforge now records which profile files each optimized kernel was built with (`applied.toml` in the store) and rebuilds when they change; an unchanged profile still reuses the existing package. The profiled `pkgver` in `round.toml` now comes from the build itself, so a kernel whose PKGBUILD computes its version during the build records the version it actually built. To adopt, redo round 2: `--autofdo=record --propeller`, reboot, `--autofdo=capture --propeller`, then `--autofdo=use --propeller`.

## Security

- **`3.1.0-F8` — PGP keys are no longer fetched from a keyserver unattended.** `import_pgp_keys` ran `gpg --recv-keys` for every `validpgpkeys` fingerprint missing from the keyring, with no prompt, no fingerprint shown and no record. `validpgpkeys` exists so a person decides who the upstream signer is, so a tampered PKGBUILD that added its own key beside a re-signed tarball had it installed silently and then passed makepkg's verification. The fetch also bypassed `freeze_sources`. Keyserver fetches now go through one consent-gated home, `build_prep.fetch_pgp_keys`, which the build-failure PGP repair also uses. The fetch is its own egress kind (`key_fetch`) and obeys the source freeze. Keys land in a throwaway keyring first, and each one's fingerprint, owner and requesting package are shown before anything is imported. Import needs a TTY confirmation (default No). A non-interactive run imports nothing and reports the fingerprints and the manual `gpg --recv-keys` command. **Batch runs** that relied on unattended imports: set `[security] auto_fetch_pgp_keys = true` (the keys are still shown). Bundled `keys/pgp/*.asc` imports are unchanged.
