# SysForge — Claude Code Context

Read DESIGN.md before proposing architecture or API changes. It is the source of truth for module layout, public APIs, CLI structure, feature status, and known gaps. Do not duplicate it here.

Repo: <https://github.com/KeithRaghubar/sysforge.git> — Language: Python, Config: TOML. The Makefile is the canonical entry point: `make test` / `make test-v` / `make lint` / `make release-{major,minor,patch}` / `make vm-*`. Don't invoke `pytest` directly.

## Dev Environment

- Ryzen 7 5800X3D, RTX 5070, Arch Linux, COSMIC on Wayland, nvidia-open-dkms
- `pkgbuild_src_dir = ~/src` (sources); builds at `~/builds`
- `etc/sysforge/` = shipped defaults (installed by PKGBUILD); `tests/data/etc/sysforge/` = the maintainer's live config for dev/testing. Separate dirs, not symlinked — update both explicitly when a change affects both.

## Known Bugs & Gotchas

1. **`tests/test_pipeline.py`** — imports from both `sysforge.primitives.config` and `sysforge.primitives.profile`. Splitting or moving symbols across those modules will break it; update the test in the same change.
2. **`match_rules` and `pkgbase`** — rules match against `pkgbase` too for split packages; don't regress this.
3. **Source sync goes through the scheduler, not `git pull --rebase`** — any new `fetch`/`update`/`build` code path that needs a fresh PKGBUILD must call `sysforge.primitives.source_sync.get_scheduler().request(SyncRequest(...))`. The scheduler handles RPC short-circuit, rate limiting, and dedup. See DESIGN.md §`source_sync.py` for status semantics (`STATUS_DIVERGED` is a warning; `STATUS_FAILED` / `STATUS_RATE_LIMITED` / `STATUS_PURGE_REFUSED` are blockers).

## Project Conventions

- **Doc update order**: DESIGN.md is the source of truth — update it first, then README.md, then CLAUDE.md. Don't update downstream docs without a corresponding DESIGN.md change.
- **Completions stay in lockstep with the CLI**: `completions/_sysforge` is updated in the same change as the CLI surface, not as a follow-up.
- **PKGBUILD parsing/detection/patching**: cross-check against `PKGBUILD(5)` before changing — easy to miss spec details (e.g. array vs string fields, escape rules). Arch-specific array families (`makedepends_x86_64`, `depends_aarch64`, etc.) are merged into their canonical key during `parse_pkgbuild`; downstream consumers (`resolve_consumes`, `match_rules`) see the merged list and never read the `_<arch>` keys directly. If a new array family is added to the PKGBUILD(5) spec, extend `_ARCH_ARRAY_FAMILIES` in `pkgbuild_meta.py`. The static parser also resolves bash brace expansion (`python-{build,installer,wheel}`) and array-parameter splices (`depends=("${_pydeps[@]/#/python-}")` via `_expand_array_refs`) against captured array globals — but it never sources the PKGBUILD, so command substitution / conditionals stay un-evaluated. Those survive as literal `${...}`/`$(...)` tokens; the AUR resolver (`aur_resolve._resolve_deps`) detects them via `_looks_unresolved` and falls back to AUR RPC `.SRCINFO` metadata for dep discovery, and the same guard (also in `pacman.collect_makedeps`) keeps junk tokens out of `pacman -S`/AUR queries. Don't hand unparsed tokens to pacman or add a parallel discovery path — extend `_apply_array_transform` for a new array-transform form, or rely on the RPC rescue.
- **lib32-* flag scrubs live at conf emit, not the profile**: `emit_makepkg_conf(is_lib32=True)` strips `-march=native` and `-march=x86-64*` ISA levels from CFLAGS/CXXFLAGS **and** lld `--icf=*` tokens from LDFLAGS for `lib32-*` builds, at both the profile-override site and the system-conf passthrough (mirrored pair). The icf scrub is **unconditional on the effective linker** — 32-bit identical-code-folding breaks links for some lib32 packages (e.g. `lib32-lzo`) even under lld — unlike the linker-gated lld-flag strip (which only fires when the effective linker ≠ lld). Both guards exist because `[profiles.bare]` (the priority-30 destination for lib32-*) is silent on these keys and would otherwise let the system conf's host-arch flags pass through to an i686 build. Don't add an i686 march/icf per-profile rule — keep the scrubs centralised, and reuse `_strip_lld_flags` for any new lld-only token.

- **`build` is a strict subset of `update` — both go through `build_core.py`**: `sysforge/build_core.py` (`build_and_install` → `prepare_deps` + per-package build loop + `install_built`) is the one shared build engine. `BuildVerb.execute` and `cmd_update`'s Phase 5/6 both call it; `update` only adds the genuinely-update-specific parts around it (version check, source-sync scheduling, `--install-only` scan, toolchain pre-flight, bulk `pacman -Syu`, summary). The per-package makepkg call always uses `strip_flags=BATCH_STRIP_FLAGS` (drops `-s`/`--syncdeps`/`-i`/`--install`) + `force_batch` so makepkg never resolves deps via pacman — sysforge pre-installs repo makedeps (`batch_install_makedeps`) and builds AUR/local deps (`resolve_aur_deps`/`build_resolved_deps`) up front, then bulk-installs. The **only** intended caller difference is `sync_source` (`update`=False, sources synced in Phase 2; `build`=`not --no-update`, inline per-package sync). Don't add a second dep-handling or build loop to either verb — extend `build_core`. `_find_existing_artifacts`/`_record_build_failure` live in `build_core` (moved from `update.py`); tests monkeypatching the moved helpers (`collect_makedeps`/`snapshot_pkg_dir`/`batch_install_pkgs`/`get_all_installed_packages` for the install path) patch `sysforge.build_core.X`, not `sysforge.update.X`.
- **LLVM source-state inspection**: `primitives/llvm_state.collect_llvm_state` is the only allowed entry point for new code that needs to inspect LLVM-toolchain source trees (variant, origin, dirty/diverged, install origin, build_mode). Do not call `git_is_dirty` + URL parsing directly — those checks drift out of sync with the rule set otherwise.
- **Dual-toolchain test parity**: any new logic that branches on the resolved compiler (gcc vs llvm/clang) must ship with both a gcc-path test and an llvm/clang-path test in the same change. Regressing one path silently is the failure mode we're guarding against.
- **CLI verbs go through the Verb framework**: every top-level command is a `Verb` subclass dispatched by `sysforge.verbs.runner.run_verb`. New verbs implement `pre_check` / `execute` / `post_validate` and set `requires_sentinel=True` if they mutate the live system. Read-only verbs (no install) leave `post_validate` as the default no-op and `requires_sentinel=False`. Argparse `set_defaults(verb_cls=XVerb)` wires the class into dispatch — do not add `func=` callbacks. See DESIGN.md §CLI Verb Framework.
- **Install-bearing scopes share one sentinel primitive**: the verb runner, the toolchain / kernel / packages pipeline stages, and the reconfigure editor-install path all use `primitives.stage_sentinel.sentinel_scope()`. Do not roll a separate `StageSentinel` install/clear path for a new install-bearing stage or verb — extend the existing primitive instead. See DESIGN.md §Toolchain stage → *Sentinel coverage map* for the current caller table.
- **`doctor` axes share one Finding framework and must stay read-only**: every `doctor` system axis is a producer returning `list[diagnostics.Finding]` (the unified shape in `primitives/diagnostics.py` — never import the `pipeline` layer from there). Register a new axis in `doctor.py`'s `_SYSTEM_AXIS_ORDER` / `_AXIS_FLAGS` / `_system_axes` with a `_collect_<axis>_findings` producer (looked up via module globals so tests monkeypatch them), add the `--<axis>` flag to `cli.py` **and** both completion files **and** regenerate the manpage (`make man`) in the same change, and extend the `_patch_axes_clean` helper in `tests/test_doctor.py` so bare/`--all` tests don't probe the real system. The probe primitives (`system_probe`/`state_probe`/`runtime_probe`) and the boot axis (`_collect_boot_findings`, reusing `kernel_safety`) are **strictly read-only** — no `pacman -Sy`, no `BuildState.save()`, no `stage_sentinel.check_and_recover_stale_sentinel` (use `StageSentinel.get_active()` to read). Guard every external command so an absent tool degrades to no findings.
- **ABI checker (`abi_check.py`) resolution is symbol-version precise — don't regress it**: exports are captured at both `sym@@VER` (default) and `sym@VER` (non-default back-compat); each undefined `sym@VER` binds to its NEEDED soname via `.gnu.version_r` only for the host/loader **skip** decision while *satisfaction* is checked against the union of all NEEDED exports (glibc sub-libs merge, so the recorded Verneed soname may not be the exporter); and an absent LLVM optional target-init symbol (`_is_optional_llvm_target_init`, reduced-target libLLVM) whose version node is present is demoted to `benign_sink`, not flagged. A genuine symbol-within-version break (e.g. `_ZNSt*@LLVM_*`) must still surface. See DESIGN.md §`abi_check.py` → *Symbol-version precision*.
- **Toolchain preflight assumes rustup is the rust delivery mechanism**: the rust cross probe in `primitives/toolchain_preflight.py` reads `$RUSTUP_TOOLCHAIN` and emits `rustup target add --toolchain <tc> <target>` as the auto-remediable fix. On a system-rust install (no rustup), the cross probe still runs but the suggestion downgrades to a non-auto pacman hint (`lib32-rust-libs` for i686). Any new cross target plugs in at `collect_required_toolchains` + the `rust:cross:<target>` token grammar — don't bolt on a parallel probe path.
- **Shipped-file changes must pass `make check-shipped`**: anything that touches `etc/sysforge/*.toml`, `PKGBUILD` / `PKGBUILD-git`, `etc/pacman.d/hooks/*.hook`, `completions/_sysforge` / `completions/sysforge.bash`, or the CLI parser (which feeds `man/sysforge.1`) gets validated by `tools/check_shipped.py`. The same checker is wired into `tools/release.sh preflight_fresh`, so drift will block a release. Schema allowlists for the configs group live in `_KNOWN_SECTIONS` / `_KNOWN_TOP_KEYS` at the top of `tools/check_shipped.py` — extend them in the same change that adds a new section/key. See DESIGN.md §Shipped-file pre-release checks for the full group list.
- **Stage-owned packages stamp `owner_stage` on `BuildState.record()`**: pipeline stages that build install-bearing packages should pass `owner_stage="<stage>"` (and `source="local"` if the PKGBUILD has no upstream remote) so `sysforge update` skips the package by default and tells the user to run the owning stage instead. The kernel stage (`owner_stage="kernel"`) and the toolchain stage (`owner_stage="toolchain"`, stamped on the install-bearing final pass only — intermediate PGO passes leave it unset) both do this; `update.py` has a per-stage config bootstrap fallback so the skip works before the first stage build has stamped the marker — `_kernel_stage_pkgbase()` reads `kernel.toml`'s `pkgname`, and `_toolchain_owns_llvm()` reads `toolchain.toml` and skips any in-scope LLVM-suite package (`is_llvm_pkgbase`) **only when** `enabled` + `compiler="llvm"` (the gcc/register-only path owns no LLVM). `--include-stage-owned` overrides the skip, and naming the package explicitly on the `update` CLI is an implicit opt-in. Both fields are sticky in `build_state.toml` — `record()` preserves the prior value when a caller doesn't pass one, so a rebuild that goes through an unaware code path doesn't erase the provenance.

- **Build failures live in a reserved `[failures]` namespace, not the install mirror**: `build_state.toml`'s top-level `[failures]` table (keyed by pkgbase) is popped into a private dict by `BuildState.__init__` and re-serialized separately, so it never leaks into `all_packages()` / `sync_with_installed()` (which must stay a clean `pacman -Q` superset). Any new code iterating `all_packages()` or touching `_serialize`/`sync_with_installed` must keep failures isolated. Failures are written by `sysforge update`'s fan-out (`_record_build_failure`) and auto-cleared by a successful `BuildState.record()` (it pops the matching pkgbase). Surfaced by `sysforge state failed`. **New build-failure diagnostics go in `primitives/build_diag.py`** as a `_match_*` signature added to `_MATCHERS` (pure-ish `(text, active) -> FixSuggestion | None`); the `signature`/`fix_cmd` ride up the build exception via `.diagnosis` (set in `makepkg_wrapper`, including the interactive-failure side-car path) and get persisted. Don't add a parallel failure-detection path.

- **Toolchain health is checked in two places — don't add a third.** `pipeline/stages/toolchain.py::_verify_llvm_install` is the authoritative post-install check (version-match across `_LLVM_VERSION_MATCH_SET` + `clang`/`lld --version` + targets + ldd; fatal on declined recovery) but only runs inside `run toolchain`. The everyday `sysforge update` path uses the lightweight `cc:<name>` probe in `primitives/toolchain_preflight.py::_probe_cc` (compiler executability + pkgver skew across the whole LLVM lockstep suite) so a broken/half-installed toolchain aborts the batch up front instead of failing every package at compiler detection. Both share one source of truth: `LLVM_LOCKSTEP_SUITE` (defined in `toolchain_preflight.py` — `llvm`/`llvm-libs`/`clang`/`lld`/`compiler-rt`/`polly`/`openmp`; excludes `spirv-llvm-translator` and `lib32-*`), which `_LLVM_VERSION_MATCH_SET` imports. The skew compares pkgver only (pkgrel stripped) and the reinstall hint is built from the installed members, so don't hardcode a package list in either place — extend `LLVM_LOCKSTEP_SUITE`. Keep these as the two entry points — the preflight check stays independent (primitives layer must not import the pipeline-layer verifier). `primitives/toolchain_safety.py` is the pure *facts* module both entry points draw from (e.g. `_verify_llvm_install`'s skew arm calls `detect_suite_skew`); it imports `LLVM_LOCKSTEP_SUITE` from `toolchain_preflight` (both primitives) and is **not** a third entry point — add new toolchain facts there, don't spawn a parallel checker. `llvm_state.detect_toolchain_config_mismatch` (used by the kernel stage and `doctor --toolchain`) is **not** a third health check — it's *provenance* reporting (does the installed LLVM's origin/profdata match what `toolchain.toml` configured?), built on `collect_llvm_state`. Don't fold compiler-executability/skew logic into it, and don't re-derive its origin check elsewhere.

- **Toolchain stage mirrors the kernel stage: three gates, build split from install, snapshot+auto-restore undo.** The pure facts live in `primitives/toolchain_safety.py` (`ToolchainFinding`, `is_brick`); the abort/warn *policy* lives in `pipeline/stages/toolchain.py` (`_gate1_preflight` / `_gate2_audit` + the Gate-3 block in `run`). LLVM builds run with `install=False` and the build functions return the built package map; the stage then runs Gate 2 (ABI hazard) **outside** the sentinel (a Gate-2 abort must leave nothing installed and no sentinel), snapshots the installed suite from the pacman cache (`pacman.cached_pkg_files_for`), and only install→Gate-3 verify→rollback run inside `sentinel_scope`. On Gate-3 failure the stage auto-restores the snapshot via `batch_install_pkgs` (offline `pacman -U`): restore-OK clears the sentinel and raises; restore-fail keeps the sentinel with a snapshot-aware `recovery_cmd`. Gate-1 bricks are overridable (`--allow-version-skew`, `--skip-build-space-check`, `require_multilib`) and downgraded to warnings in `--dry-run`. The pkgver-skew check (`check_pkgver_lockstep`) is **lockstep-members-only** — `spirv-llvm-translator` and `lib32-*` are excluded so their legitimately-different versions don't false-positive (this is why the old whole-set `_check_pkgver_consistency` was removed). The GCC path is register-only and skips all gates. New toolchain safety facts go in `toolchain_safety.py`, not inline in the stage; don't add a parallel undo path — extend the snapshot/rollback helpers. Dual-toolchain test parity applies (gcc register-only path + llvm gated path).

## Toolchain & kernel stages

`run toolchain` (stage 6), `run kernel` (stage 8), and the PGO-toolchain profdata-reuse path in `sysforge update` (`build_mode = "pgo_llvm_toolchain"`) are stable as of v1.x (re-promoted from the v1.0 experimental classification). They still default to `enabled = false` in `toolchain.toml` / `kernel.toml` because building a custom toolchain or kernel is an opt-in decision; do not flip the defaults under the assumption that "no longer experimental" means "on by default".

`run toolchain` defaults to `compiler = "gcc"` when the key is unset; LLVM is opt-in only. The shipped `[profiles.standard]` uses system gcc/binutils; LLVM components (`clang`, `lld`, `llvm`, `compiler-rt`) live in `optdepends` and are only required when the LLVM profile or `run toolchain --compiler=llvm` is selected.

**Toolchain stage never builds GCC.** The `compiler = "gcc"` path is register-only — it writes the system `/usr/bin/gcc` paths into pipeline state and returns. Stock `gcc-libs` from `base-devel` provides the runtime. Do not reintroduce a `_build_gcc` helper or any code path that runs `makepkg` for `gcc`/`gcc-libs` under the toolchain stage; if a future change needs a GCC build path, it lives in `packages`, not here.

**Kernel stage compiler is independent of the toolchain stage.** `kernel.toml compiler` (and `sysforge run kernel --compiler {gcc,llvm}`) lets the kernel use a different compiler than the system. Resolution: CLI flag > `kernel.toml compiler` > toolchain-stage pipeline state. Use the `_compiler_paths` helper in `sysforge/pipeline/stages/toolchain.py` when mapping the resolved name to cc/cxx paths — don't hardcode `/usr/bin/clang` etc. anywhere else.

**Kernel stage is interactive by default.** Unlike the other stages, `sysforge run kernel` defaults to running the PKGBUILD's interactive kconfig target (typically `make nconfig`). The non-interactive path is opt-in via `--non-interactive` or `kernel.toml interactive = false`. This is the only verb in the CLI where the unattended path is opt-in rather than opt-out; preserve that asymmetry.

**Kernel stage must never leave the system unbootable — three gates, and the build is split from the install.** The boot-safety facts live in `primitives/kernel_safety.py` (pure, never imports the pipeline layer); the abort/warn *policy* lives in `pipeline/stages/kernel.py` (`_gate1_preflight` / `_gate2_audit` / `_gate3_verify`). Brick-class findings (`KernelFinding.is_brick`) hard-fail; everything else warns. The stage builds with `BuildOptions.no_install=True` so the resolved `.config` can be audited (Gate 2) *before* `install_built_packages()` runs — because Arch's pacman hooks build the initramfs/boot-entry at install time, a post-build audit is only meaningful if the install is held back. Consequences to preserve: the build + Gate 2 run **outside** the sentinel (a Gate 2 abort must leave nothing installed and no sentinel); only install→mkinitcpio→bootloader→Gate 3 are inside `sentinel_scope`. New boot-critical kconfig symbols go in the curated tables in `kernel_safety.py` (`_CORE_BOOT_KCONFIG`/`_ROOT_FS_KCONFIG`/`_STORAGE_KCONFIG`/…), not inline in the stage. New device→`CONFIG_*` mappings go in `device_probe._MODULE_TO_KCONFIG`. Don't add a parallel boot-readiness check elsewhere — extend these.

**Kernel/device health has one inspection entry point per layer.** `device_probe.enumerate_devices` is the only allowed way to inventory PCI/USB devices and resolve modalias→module→`CONFIG_*` (don't re-parse `modules.alias` or hardcode module names elsewhere). `kernel_safety.parse_kconfig_text` is the single `.config` line parser — `dep_analysis._parse_kernel_config` (running-kernel reader) already delegates to it; reuse it rather than re-implementing the `CONFIG_X=`/`# … is not set` parse.
